# Maintenance

> Rules and their reasons, compressed. Trust the code over the docs when they disagree, and fix the doc in the same commit.

The fleet home stage gets a **Maintenance** view beside **Activity**, and the project dashboard gets **Today | Maintenance** tabs. Both answer one question per project: what is rotting while nobody looks. The answer is spread over seven **facets**, and every facet can be fed by any CI, any security reporter, any update bot or any forge. The whole feature is built so that a new vendor is one manifest row and one Rust read function, and that a vendor nobody has written an adapter for yet says *can't check (Woodpecker)* instead of looking healthy.

## The model

- **Seven facets, fixed and closed**, always in this order: `ci`, `security`, `deps`, `release`, `git`, `prod`, `work`. A card draws all seven in fixed positions, so the eye learns where CI is.
- **A source is one adapter for one facet**: `github-actions`, `gitlab-ci`, `dependabot-alerts`, `renovate-prs`, `git-tags`, `osv`… A facet has any number of sources, and several may apply to one project at once (Dependabot *and* `cargo audit`). A facet cell is the merge of its sources' reports.
- **A marker is a source we can recognise but not read yet** (a `Jenkinsfile`, `.woodpecker.yml`, `.snyk`). It exists so the cell says *can't check (Jenkins)* rather than *no CI*. Promoting a marker to a source is the normal way the feature grows.
- **Rust reads facts; TypeScript decides.** Rust detects what applies, runs the read, normalises the vendor's vocabulary (`MODERATE` → `medium`, `timed_out` → `fail`; that is a fact, and the raw value is kept beside it) and returns a typed coverage. Whether that is *failing 1d*, *drifting* or *needs you*, and in what order cards stand, is `maint.ts`'s. Thresholds are data a team can override, never constants in Rust (the `health.rs`/`health.ts` split).
- **The frontend never names a vendor.** GitHub Actions, GitLab CI and Woodpecker all arrive as `CiRuns`; a cell, a finding and a brief are written against the fact shape. `provider-contract.test.ts`'s rule, one level over: a feature gated on a vendor id is a feature the next vendor silently lacks.

## Coverage: unknown is never green

Every report carries a `Coverage`, and only `ok` carries facts.

| state | means | example |
|---|---|---|
| `ok` | read; facts follow (possibly empty) | 3 workflows, one failing |
| `off` | the feature is switched off on the forge | Dependabot alerts disabled; code scanning "no analysis found" |
| `noAccess` | we could not see it, with a `fix` | token lacks `security_events` → `gh auth refresh -h github.com -s security_events` |
| `noTool` | the CLI it needs is missing or not logged in, with a `fix`; or no token is saved for the service's host, with none (Settings › Accounts is the door) | `glab` not installed; `cargo-audit` absent; *a token for sentry.io not available* |
| `unsupported` | detected, cannot be answered | no default branch known; GitLab vulnerabilities need Ultimate |
| `notRun` | a click-only source nobody has clicked on this machine | `npm audit`, prod URL check |
| `error` | anything else, the reason verbatim | |

`facetCell` resolves a cell top-down, and **only the last step can draw the grey dot**:

1. `[maintenance] off` names the facet → *not tracked*, muted.
2. Not detected yet, or a read still out → *unread*: `—` / a skeleton, never a dot (`dirtyTag`'s three states).
3. No source and no marker → *none*, phrased per facet: *no CI*, *no update bot*, *no release*, *no deploy*.
4. Markers only → *can't check (X)*, the tip naming what was found.
5. Sources, none `ok` → *can't check*, said as its reason and never bare: the most actionable coverage (`COV_RANK`: `noAccess`, `noTool`, which carry a fix, then `off`, `error`, `unsupported`, `notRun`) names the cell in `whyWord`'s few words (*token scope*, *token refused*, *no access*, *signed out*, *no token*, *tool missing*, *alerts off*, *read failed*, *unavailable*, *not checked*; *skipped here* for a source this machine skips, and *not allowed here* for a `[deploy] host` it has not ticked, but only where no other source of the facet could still be asked), muted, and the tip lists every one in that order. *Unavailable* too is said only where nothing else could still be asked: beside a source nobody clicked it would read as the facet being down (Prod, beside a `.de` domain no registry answers for), so that cell says *not checked*.
6. At least one `ok` → the facet rule over the `ok` facts. **`ok` needs positive evidence**: CI with zero runs on the default branch is *never ran*, not a pass (the `prReady` rule), and CI is the grey dot only when every workflow's newest run passed or skipped (one cancelled or unknown beside a pass reads *1 cancelled*); re-runs read without the default branch's runs are `blind` (*runs not read*), so a failed `github-actions` read keeps the cell *can't check* with its own reason, or, once they found a flaky job, amber for that alone (*runs not read · 1 flaky job*) with Coverage still listing the failed read; Security is clean only if a security source answered; a bot that is configured but has opened nothing for 30 days is *silent*, not healthy.
7. Partial coverage is stated, never hidden: *Dependabot clean · npm audit never run*. A list that hit its page cap (`truncated`) prints its count as `100+`.

**A facet with a second kind of facts judges each kind on its own and combines them through `worseOf(a, b)`** (`maint.ts`), `b` null when its kind has no facts: the worse level speaks, both tips are kept, and the older fetch dates the pair. A kind's judge may return `blind`: what it read cannot answer the facet alone (a supported runtime vouches for no advisory). A blind verdict speaks over one that answered only with something it found (`bad`, `warn`, `info`), never with an unknown or a pass. The pair is blind only while both are and neither found anything. The same rule holds at step 6: `facetCell` turns a blind verdict into *can't check*, naming the source that failed (or *can't check (X)* beside a marker nothing reads), only when it found nothing, so what a blind kind found is drawn like any other answer. CI (re-runs), Release (deployments), Deps (packages) and Prod (hosts, domains, errors) each gain their second kind this way: `RULES` holds one line per facet, and that facet's line is the one a slice edits. Prod is the first with more than two coming, so `prodRule` is `PROD_JUDGES`: one judge per kind, the worse speaking, each declaring whether it `alone` may vouch for the cell (probes, hosts and errors may; a kind that never can is judged blind). Domains never can: a registration read alone that found nothing is *addresses not checked* (or *not checked* beside the probe nobody ran), while one being lost colours the cell by itself.

**Deps' second kind is a ranking, never a colour.** Nearly every repository is a major behind on something, and a rule that fires on ordinary code is worse than no rule (`health.ts`'s), so `Packages` is `info` at its loudest: *5 behind* touches no badge, band, `needsCount` or `rankMaint`, and no threshold raises it. With nothing behind it is muted *3 unplaced* when something could not be placed (from git, not on the registry, a name that did not answer) or *partly read* past the read's cap or beside a gap (a `yarn.lock`, a lockfile version no parser knows, one too large), and the grey dot only when every one was placed and every lockfile read; a count over a gap carries a `+` as a capped one does. It is **blind**: a registry read says nothing of whether anything opens updates, nor of what another registry would answer. So with no bot's answer beside it, a read that found nothing is *can't check*, named for the source that failed or that nobody asked, and *can't check (Renovate)* beside a marker. Beside a bot that did answer, its own unknown still speaks, since no bot can answer that: *3 unplaced*, never the dot. A bot nobody set up beside packages that were read says *no update bot* in the tip rather than over them; a registry nobody asked leaves *no update bot* as it was. `wantsSetup` asks the update bots alone, so a project whose only deps source is a registry keeps its *Set up*: a registry read says nothing about whether anything opens updates. For the same reason a registry's answer beside a failed bot read reaches no verdict on the facet (`vouched`): *5 behind* is drawn, Coverage lists the failed read, and the snapshot keeps the last known red.

Release and Git counts, and how far an environment is behind, are as old as the last fetch, and Maintenance never fetches (that is `autofetch.ts`'s job). Their facts carry `fetched_at`, the newest `FETCH_HEAD` mtime of the repo and its worktrees (each checkout writes its own), and the tip says *as of last fetch 3d ago*; past a week it drifts on its own.

## Cost classes: nothing runs until asked

Each source declares one `cost`, and **Rust enforces it**, not a convention at the call site.

| cost | may do | runs in a scan | runs on a click |
|---|---|---|---|
| `local` | read files, read-only `git` through `git_cmd` | yes | yes |
| `forge` | read the forge through the user's own CLI credential (`gh`, `glab`) | yes | yes |
| `public` | send data to a third-party public service (OSV.dev gets package names) | only if this machine opted in | yes, one-off |
| `tool` | execute a program in the project (`npm audit`, `cargo audit`, `trivy`) | **never** | yes |
| `remote` | touch the user's infrastructure and what reports on it (HTTP to `[deploy] urls`, TLS, ssh with `BatchMode` and `StrictHostKeyChecking=yes`, the error tracker `[deploy] sentry` names, with a token Episko sealed for its host) | **never** | yes |

`maint_read` takes a `mode` (`scan` or `explicit`) and a `public` flag, and refuses anything its class does not permit with `notRun`; the TS-side `runnable()` is a convenience, not the guard. It also takes `hosts`, this machine's ticks, and `ssh-host` answers `notRun` and connects nowhere unless the `[deploy] host` the file names now is among them, so a pull cannot move a click to another machine. A `tool` source is in the class `<pm> outdated` is in, and follows its rules (`docs/dependencies.md`): on a click, through `run_capped`, never on a load path, and a non-zero exit with a report is findings. On Windows it starts through `cmd.exe /D /C`, since npm and pnpm are `.cmd` shims `CreateProcessW` cannot start, so `SysExec` refuses any argument cmd would read as syntax. A `public` source's manifest row carries `sends`, and every door to it says who receives what (`disclosure`): the Settings switch that lets a scan ask it, and the *Check with* row that asks it once.

**A scan is triggered only by a person:**

- **Fleet:** switching to the Maintenance view when the cache is empty or older than `MAINT_FRESH_MS` (10 min), or ⟳ (forced). Landing on Maintenance at boot (`cc-fleet-view` persisted, and nothing restored took the stage) counts as that switch: it paints the last session's scans from `cc-maint-scan`, whole, and `maintOnBoot` (called once by main.ts after the boot picks its stage and the roster, the adopted panes and the first externals poll have settled, so the scan and its *checked* stamp cover every project rather than the favourites alone; never from `openFleet`, which every exit from the stage runs) scans when any of them is older than the window. While a re-read is out, a card drawn from the earlier answer is dimmed (`stale`) and its sub says *reading 4 of 9 · as of 3h ago*; a tab dims whole. A sweep says how far it is (*Scan progress* under *Surfaces*). Booting onto Activity, or onto a session, scans nothing. `openFleet`, `loadFleet`, `renderFleet` and `buildView` never reach `maintscan`'s scans (they read its cache only), because `openFleet` runs at boot and on every exit from the stage (`docs/dashboard.md`'s *a fleet-wide sweep is exactly the "nothing runs until you ask" rule*). Choosing the tab is the ask that buys the sweep.
- **Project dashboard:** the first switch to the Maintenance tab per open scans that one project (`loadMaint`, shaped like `loadBranches`), and so does an open that lands on the tab (a fleet card's name, a *Review*). `renderDash` and the tab's count read the cache only; an account switch re-asks through `reloadDashGh`.
- **Explicit buttons:** *Run npm audit*, *Check with OSV.dev*, *Check prod*. Each names what runs or what leaves the machine. Where they sit is *Offers are not findings* below.

The *Since last week* band (*Surfaces* below) reads only the marks finished scans leave and asks nothing: a Monday look at the view is the ask that buys the week's last scan, and no cadence or timer exists.

A test reads the source of those four functions and fails if any of them reaches anything of `maintscan`'s or `maintui`'s beyond the cache reads it lists, and holds the header chip (`./maintpop`: its paint and opening its popover) to the same, its *Check* being the one scan it may reach. Once anything was checked, a project with no answer (added since, or forgotten on an account switch) is drawn as an unread card, so the all-clear never speaks for it.

A scan asks `maint_read` for **every** detected source the machine does not skip, not only the ones `runnable` offers: for a class the scan may not run, Rust's gate answers `notRun` (or the result a click left, kept 24 h) without running anything, so no facet waits forever on a read nobody makes. `maint_detect` and `maint_read` share the six slots, and a person's click goes ahead of whatever a scan still has queued.

## Detection

`maint_detect(root)` reads the remote, the files and `.episko/episko.toml`, and spawns nothing beyond the git remote read `project_facts` already does (plus, with no `origin`, the `git remote` listing that finds the primary remote, so the forge and the trunk come from one remote). It is cached per root for 30 s, so `maint_read`'s own applicability check (a stale frontend list must not run a source that no longer applies) does not walk the tree once per source.

- **The forge is decided before files.** `.github/workflows/` means GitHub Actions on github.com and Forgejo Actions on Codeberg; Renovate runs on every forge. Order: the `[maintenance] forge` pin, then a known-host table (`github.com`, `gitlab.com`, `codeberg.org` → forgejo, `bitbucket.org`, `dev.azure.com`/`*.visualstudio.com`), then a host containing `gitlab`/`gitea`/`forgejo`, then `unknown`. No network probe: a self-hosted host that names nothing stays `unknown` until pinned, and the tip says how. `git::split_remote` is already `pub(crate)`; `ssh_hostname` becomes it. The forge's `path` is everything after the host, not two segments: GitLab subgroups are `group/sub/repo`.
- **Files are probed, never executed**: a fixed list of paths at depth ≤ 2 under `SKIP_DIRS`, where a trailing `/` means a non-empty directory and `file#key` means a key inside a JSON file (`package.json#renovate`). The list is the union of the manifest's `detect` entries. An entry holding a `/` or starting with `.` is anchored at the root (GitHub reads `.github/workflows/` there and nowhere else); a bare name (`Jenkinsfile`, `Cargo.lock`) is also looked for one directory down, never inside a dot directory or `SKIP_DIRS`.
- **The git sources detect `.git`**, which is how a folder that is not a repo gets *not a git repository* rather than a Git cell that cannot answer. `[maintenance] off` and `sources` are applied in detection too, so `maint_read` refuses a source the file switched off (`unsupported`, *switched off in .episko/episko.toml*) and an off facet carries no markers.
- **Worktrees collapse to the repo root.** Facts are keyed by `repoRoot ?? path` (as `loadFleet` keys heads); a card is one per project.

## The manifest: `src/maintmanifest.json`

One checked-in file read by both sides, the `providers/manifest.json` precedent: Rust via `include_str!`, TS via `resolveJsonModule`. It sits flat in `src/` because the comment, IPC and sync gates do not recurse.

```jsonc
{
  "sources": {
    "github-actions": { "facet": "ci", "label": "GitHub Actions", "cost": "forge",
                        "forge": ["github"], "detect": [".github/workflows/"],
                        "sees": ["ci.default-branch", "ci.per-workflow", "ci.failing-since"],
                        "blind": ["ci.other-branches"] },
    "git-tags":       { "facet": "release", "label": "git tags", "cost": "local",
                        "forge": [], "detect": [], "sees": ["rel.unreleased", "rel.last"] }
  },
  "markers": [
    { "facet": "ci", "label": "Woodpecker", "detect": [".woodpecker.yml", ".woodpecker.yaml", ".woodpecker/"] }
  ],
  "bots": [
    { "id": "renovate", "logins": ["renovate[bot]", "app/renovate", "renovate-bot"],
      "branch": "renovate/", "dashboard": "Dependency Dashboard",
      "config": ["renovate.json", "renovate.json5", ".github/renovate.json", ".github/renovate.json5",
                 ".gitlab/renovate.json", ".renovaterc", ".renovaterc.json", "package.json#renovate"] }
  ]
}
```

- `facets` lists the seven in card order, each with its label and its *none* phrase (*no CI*, *no update bot*), so both sides phrase step 3 of `facetCell` from one place.
- `needs` (optional) names the config a source reads and that must be set before it applies: `sarif-files` has `"needs": ["sarif"]`, so a project that names no SARIF file has no such source and its Security cell can still say *no security source*; `http-probe` has `"needs": ["deploy.urls"]`, an address in `[deploy]`, `ssh-host` `"needs": ["deploy.host"]`, `deploy-tags` has `"needs": ["deploy.envs"]`, a tag convention there, `rdap-domain` `"needs": ["deploy.domains"]`, an address whose host has a registered domain under a public suffix (`maint_rdap::domains_of`: no IP, local name or platform's subdomain), and `sentry-issues` `"needs": ["deploy.sentry"]`, an `org/project` `keep` accepted. The keys are a closed list (`NEEDS`: `sarif`, `deploy.urls`, `deploy.host`, `deploy.envs`, `deploy.domains`, `deploy.sentry`, read by `needs_met`: `MaintConfig::has` for `[maintenance]`'s, the detection's `[deploy]` for the other five), and `Manifest::check` refuses any other.
- `forge` restricts a source or a marker to the forges it can talk to; empty means any, and a list of `!x` entries means any forge but those (never mixed with plain ones), so a marker that steps aside for a GitHub-only source cannot silently miss a forge added later. An empty `detect` means "applies whenever the forge matches", so a marker needs at least one of the two or it would claim every project. A marker label may hold `{host}` (*CI on {host}*), filled from the remote.
- Rust parses the file with `deny_unknown_fields` and `Manifest::check` refuses it at load (the `providers/manifest.json` precedent): the seven facets in order, source ids equal to `SOURCES`, kebab-case ids, known forge ids, relative `detect` paths, every capability in `MAINT_CAPS`, and a complete `bots` row. A field the manifest does not define (an `argv`) fails the build's tests.
- `settings` (optional, a forge source of one forge only) is the https page that switches the source on, `{path}` the repository's: the three GitHub security sources name `security_analysis`. `settingsUrl` fills it only for an `off` coverage on a forge the source talks to, never for a pinned host the template does not name, and only for a path that is one `owner/repo`; so the link is data like the label, and `maint.ts` names no vendor.
- `queue` (optional, a work source only) says the dashboard's Today queue lists that source's issues and pull requests (`github-work`: the queue reads the slug `gh` is handed), so the Work board's counts open it (`WorkRow.queue`); a project whose work another source read keeps plain numbers.
- `sends` (required on a `public` source, refused on any other) is what leaves the machine, as a phrase: `disclosure` makes it the sentence *OSV.dev receives the name and version of every package in this project's lockfiles. Nothing else leaves this machine.*, which the Settings switch takes as its hint and the *Check with* row as its detail.
- `token` (optional, a `forge` or `remote` source only) is a service token Episko seals for a service with no CLI of its own: `{id, label, host, page, scopes}`. `id` is a kind `maint_tokens::KINDS` keeps (bearer only, until a kind needs another scheme), `host` the default slot Settings offers, `page` the https page that makes one with `{host}` filled, `scopes` what a read needs. All of it is data, so Settings › Accounts draws one control per kind (`tokenKinds`) and `maint.ts` names no vendor. `Manifest::check` refuses a token on any other cost class, a kind with no `KINDS` row, a host that is not a plain lower-case name, a page that is not https with `{host}`, empty scopes, and any field it does not define (a `scheme`).
- `sees`/`blind` are a **closed capability vocabulary** (`MAINT_CAPS`). TS's `capsOf()` throws on an unknown one and Rust mirrors the list, the `providerCapabilities` rule: a misspelt capability must fail, not quietly drop a line from the coverage card.
- `bots` is the update-bot table `deps::bot_of` reads (it replaced a closed match and its dead TS twin `isBotPr`). A login matches with `[bot]` and `app/` ignored, since one App spells itself both ways. `[maintenance] bots` adds logins, which join Renovate's row (self-hosted Renovate); a closed match silently files their PRs on the human Open-work board. Every bot has a `<id>-prs` source, and a marker that stands in for one off its forges detects exactly its `config` files.
- **Only the compiled-in manifest defines what runs.** No argv or binary ever comes from `.episko/episko.toml`, and a URL it names carries a credential only under `Auth::Sealed`'s rule (below): a committed table may select, disable and parameterise built-in ids, so a teammate's commit cannot make your Episko run a binary. A committed host (`[maintenance.params] sentry_url`) is a parameter of that kind and no more: it **only selects among the slots the person saved** (the hosted service's two regions share its slot, so `https://de.sentry.io` reads with the token saved for `sentry.io`, and no other `*.sentry.io` has a slot at all), the token goes only over https to a host whose own slot is exactly that one, and nothing is sent when none is saved. A service with no CLI of its own has its token sealed by Episko (Settings › Accounts, `maint_tokens.rs`); every other credential stays where its CLI keeps it.

## Wire types

Rust, `#[serde(rename_all = "camelCase")]`, tagged enums:

```rust
#[serde(tag = "state")] enum Coverage { Ok, Off { reason }, NoAccess { reason, fix: Option<String> },
    NoTool { tool, fix: Option<String> }, Unsupported { reason }, NotRun, Error { reason } }

struct SourceReport { source: String, facet: Option<Facet>, cost: Option<Cost>, coverage: Coverage, // None: an id the manifest does not know
    at: Option<u64>,      // unix secs the read finished; a cache hit keeps the original
    truncated: bool,      // a list hit its page cap: counts are floors
    gaps: Vec<String>,    // honest partial support: "yarn.lock not read"
    facts: Option<Facts> } // Some only when coverage is Ok

#[serde(tag = "kind")] enum Facts {
    CiRuns     { branch: String, runs: Vec<CiRun> },          // default branch only, newest first, ≤ 50
    CiReruns   { days: u32, since: Option<u64>, runs: u32, reran: u32, jobs: Vec<RerunJob> }, // every branch; since: a cut window
    Advisories { items: Vec<Advisory> },
    UpdatePrs  { bot: String, configured: bool, prs: Vec<UpdatePr>, dashboard: Option<u64> },
    Packages   { items: Vec<PkgLatest>, current: u32 },           // items: behind or unplaced; current: at their newest, only counted
    Release    { trunk: Option<String>, tag: Option<String>, tag_at: Option<u64>, since: u32,
                 oldest_unreleased_at: Option<u64>, tags_seen: u32, fetched_at: Option<u64> },
    Releases   { latest: Option<ForgeRelease>, count: u32 },
    Changelog  { unreleased: Option<u32>, latest: Option<String>, latest_at: Option<u64> }, // None: no Unreleased section
    Deployments { trunk: Option<String>, envs: Vec<Deployed>, fetched_at: Option<u64> },
    Hygiene    { trunk: Option<String>, unpushed: Option<u32>, local_only: Vec<String>, merged: Vec<String>,
                 gone: Vec<String>, branches: Vec<BranchAge>, worktrees: Vec<WtAge>, fetched_at: Option<u64> },
    Work       { issues: u32, prs: u32, review_requested: Option<u32> },
    Probes     { items: Vec<Probe> },
    Hosts      { items: Vec<HostFacts> },
    Domains    { items: Vec<Domain> },
    Errors     { project: String /* org/project as linked */, environment: Option<String> /* None: every one */, window_days: u32,
                 release: Option<ErrRelease>, last_event: Option<u64>, url: Option<String>, issues: Vec<ErrIssue> /* newest first seen first, ≤ 100 */ },
    Runtimes   { items: Vec<Runtime> } }

struct CiRun    { workflow, status /* pass|fail|running|cancelled|skip|neutral|unknown */, raw, sha, at, url }
struct RerunJob { workflow /* `CI (nightly.yml)` when two share a name */, job, reruns, passed, steps /* ≤ 3, most often first */,
                  seen: Vec<Rerun> /* newest ≤ 3 */ }
struct Rerun    { sha, branch, at /* the failed attempt's start */, passed, url /* its job page: the log */ }
struct Advisory { id, aliases: Vec<String>, kind /* dependency|code|secret|config */, pkg, ecosystem,
                  version, severity /* critical|high|medium|low|unknown */, raw_severity, summary,
                  fixed, location, url, tool }
struct Probe    { name, url, code: Option<u16>, ms: Option<u32>, cert_not_after: Option<u64>, err: Option<String> }
struct Domain   { domain /* as asked, an IDN as its A-label */, names: Vec<String> /* the [deploy] entries under it */, expires: Option<u64> /* None: the registry publishes none */, status: Vec<String> /* RFC 8056's words */, registrar: Option<String>, url: Option<String> /* the registrar's own page */ }
struct ErrIssue { id, short_id, title, culprit: Option<String>, level /* fatal|error|warning|info|debug|unknown */, raw_level,
                  trend /* new|regressed|escalating|ongoing|unknown: the tracker's substatus */, raw_trend, events, users,
                  first_seen: Option<u64>, last_seen: Option<u64>, unhandled: Option<bool> /* None: not said */, url: Option<String> }
struct ErrRelease { version, at: Option<u64> /* released, else made */, new_issues: Option<u32> }
struct TraceAnswer { id, trace: Option<ErrTrace>, err: Option<String> }   // maint_trace's own wire, never in a report
struct ErrTrace { exceptions: Vec<ErrException> /* ≤ 3: the root cause first, the one raised last at the end */, exceptions_cut /* the middle dropped */, message: Option<String> }
struct ErrException { kind, value /* ≤ 500 chars */, frames: Vec<ErrFrame> /* ≤ 40, innermost last */, frames_cut /* outer past 40, or naming no file or function */ }
struct ErrFrame { file: Option<String> /* a page's query dropped */, line: Option<u32>, function: Option<String>, in_app }
struct HostFacts { alias, os: Option<String>, now: Option<u64> /* the host's clock */, uptime: Option<u64>, load: Option<[f64; 3]>, cpus: Option<u32>,
                   disks: Vec<Disk> /* `/` first, ≤ 16 */, updates: Option<u32>, security: Option<u32> /* None: the manager cannot tell */,
                   packages: Vec<String> /* security first, ≤ 40 */, pm: Option<String>, lists_at: Option<u64>, reboot: Option<bool>, reboot_why: Vec<String>,
                   containers: Option<Vec<HostContainer>> /* None: no runtime, or not readable */, compose: Vec<String> /* as `[deploy]` names them */ }
struct Disk     { mount, size_kb, used_kb, avail_kb }
struct HostContainer { name, image, state /* the runtime's own word */, health: Option<String>, restarts: u32, exit: Option<i32>,
                   started_at: Option<u64>, project: Option<String>, service: Option<String> }
struct Runtime  { product /* the list's id: nodejs */, name /* node */, declared, cycle: Option<String> /* None: unlisted */,
                  eol: Option<Eol> /* untagged: unix secs, or a bare true/false */, latest, newest, file, url: Option<String> }
struct UpdatePr { number, title, url, branch, draft, at: Option<u64>, checks: CiStatus }
struct PkgLatest { name /* its own, an npm alias resolved */, ecosystem /* lockfile.rs's: npm, crates.io */, importers: Vec<String>,

- `Forge.by` says how the kind was decided, so a tip can say *pin it in `[maintenance] forge`* exactly when nothing else could tell. The host stays as the remote spells it: an ssh alias resolves for the decision and is shown as written. Where an API is asked, when that is not the host as written, is kept as `api` (`#[serde(skip)]`, never on the wire), and `api_host()` is where `glab --hostname` points, since glab stores its credentials per real host: an alias's resolution when the alias is a bare name or only its resolution is in the host table (a dotted host whose ssh goes to an IP or a separate ssh endpoint stays the web host), and an http(s) remote's host *with* its port when that is not the scheme's own (glab keys a login by `host:port`).
- `CiReruns` is its own kind because `CiRuns` means *the default branch only, newest first*, and every reader of it (`ciFailures`, `ciFlows`, the CI board's strip, Today's `ciRows`) takes its runs as that branch's history: a pull request's failed first attempt filed there would read as a red default branch. Only jobs that passed on a re-run at least once are on the wire; `runs` and `reran` count what was read, and `reran` is the runs whose jobs show two attempts, since `run_attempt` alone also rises when a fork's workflows are approved.
- `Deployments` is its own kind because `Release` is one tag per project and `Probes` an HTTP answer. `maint_repo::norm_deploy` is the one map into `DeployState`, with the raw word beside it; `maint_git::env_tier` is a vocabulary map from a name to `EnvTier`, the raw name kept: it lives in Rust because it must spell `github-pages`, and a name it does not know is `other`, listed and never amber. A forge's production flag is no help: GraphQL has none, and REST's was false even for a hosted platform's Production.
- `Changelog` is its own kind because an *Unreleased* section is neither a tag nor a published release. Its entries are top-level bullets (`-`, `*`, and this repo's `+ ~ !`), with prose and no bullet counting as one.
- `Errors` is its own kind because `Advisories` is Security's and would merge errors with code-scanning alerts, `Probes` holds no list of issues, and `Work` is counts only and would lose *new since the release*. `maint_err::level` and `trend` are the one map into `ErrLevel`/`ErrTrend`, the raw words beside them; an older self-hosted tracker sends no substatus, which is `unknown`. Only words and counts are on the wire: never an event, a stack trace or a user, since a kept scan (`cc-maint-scan`) holds it. *Fix*'s stack traces have a wire of their own (`TraceAnswer`, `maint_trace`'s answer), read on that click and handed to the brief, so a trace never reaches a report, a cache or a `cc-` key.

- **One CI vocabulary.** `maint_ci::norm_status(raw)` is the only map from a vendor's status to `CiRun.status` (case-blind; `check_status(status, verdict)` reads a run's status until it completes). GitLab's words joined it in slice 9 (`failed`, `canceled`/`canceling`, `created`, `preparing`, `waiting_for_*`, `running` and `scheduled` as running, and `manual` as `neutral`: a pipeline held at a blocking manual job, typically a deploy gate, has failed nothing and runs nothing, so it is neither activity nor a pass, and the CI cell's tip names the raw word); none is a word GitHub sends, so no pinned verdict moved. `review::normalise_check` (the review's five words) and `deps::roll_checks` (the rollup's buckets) are projections of it, and agree: `cancelled` and `stale` (GitHub stopped waiting, no verdict) fail, `neutral` passes the rollup as GitHub's merge rule has it, and a word nobody taught us is `unknown`, which both read as pending, never as a pass or a failure. Today's outcomes were pinned first in `testdata/maint/check-verdicts.json`; a `*Was` field marks each verdict that changed, and each is in the CHANGELOG.
- **`Advisory.id` is generic** (GHSA, CVE, OSV, RUSTSEC, a scanner's rule id) and `aliases` carries the rest, so `mergeAdvisories` folds Dependabot, OSV and `cargo audit` reporting one CVE into one row at the worst severity. Names match case-blind (`cve-` meets `CVE-`), and a row keeps one spelling of each. A `code`, `secret` or `config` finding is keyed by its id **and its `location`**: a rule firing in two files is two findings, while GitHub code scanning and a CodeQL SARIF file reporting one place are one. The row's `key` is that identity. A card line is not a row: `findings` folds every row of one kind into one line (*One line per kind* below), and the tab's detail cards may still list the rows.
- **The wire is pinned by a fixture.** `wire_fixture_is_current` (cargo) serialises a fixed report covering every `Coverage` and `Facts` variant and compares it with `test/fixtures/maint-wire.json`, `maint_trace`'s answers under its `trace` key; `test/maint.test.ts` reads the same file and asserts `narrowMaint` and `narrowTrace` accept it and every `state`/`kind` is in the TS unions. Regenerate with `MAINT_WIRE_WRITE=1 cargo test`. A renamed field fails on both sides.
- **`narrowMaint` narrows rather than trusts**: a report of the wrong shape becomes an `error` coverage for that source alone.

struct Ctx<'a> { root: &'a str, cfg: &'a MaintConfig, forge: &'a Forge, account: Option<&'a str>, force: bool, hosts: &'a [String] }   // force reaches deps.rs's shared caches; hosts: this machine's ticks

struct Read { facts: Facts, truncated: bool, gaps: Vec<String> }   // a Facts kind outside the source's facet is an `error`

trait Exec: Sync {
    fn gh(&self, root: &str, account: Option<&str>, args: &[&str]) -> Result<String, String>;
    fn glab(&self, root: &str, args: &[&str]) -> Result<String, String>;
    fn tool(&self, root: &str, bin: &str, args: &[&str], secs: u64) -> Result<Output, String>;
    fn http(&self, req: &HttpReq) -> Result<HttpResp, String>;   // absolute curl path
    fn ssh(&self, alias: &str, script: &str, secs: u64) -> Result<Output, String>;
    fn on_path(&self, bin: &str) -> bool;
    fn has_auth(&self, kind: &str, slot: &str) -> bool;   // a sealed token is saved there, so a read with none asks nobody
}
```

- **`Exec` is the only side-effect seam**, in the inline `maint::exec` module. `Output` is maint's own (`code`, `stdout`, `stderr`) so `FakeExec` can build one. The module's `dead_code` allow went in slice 33, when the first adapter sent a token; one stays on `Auth::Env`, since `ENV_TOKENS` is empty until an adapter needs an env token. `HttpReq.report` is a probe: curl sends nothing, throws the body away (`-o` to the null device) and prints `-w '%{json}\n%{certs}'`, which comes back as the body; a transfer that failed is still a report, since `%{json}` carries `exitcode` and `errormsg`. `http_answer` reads curl's `-w` trailer as the status and a non-zero exit as curl's own error, with one exception: exit 56 beside a status that is not 2xx is that status. Schannel reports a server closing without close_notify as a receive error after the answer is in, and Verisign's empty 404 for an unknown name arrives exactly so; a 2xx beside it may be a body cut short, so it stays an error. `SysExec` wraps `github::gh`, `forge::glab`, `deps::run_capped`, `platform::sys_command` + `augmented_path`, and the absolute curl paths `telemetry.rs` already uses (a GUI app's PATH is stripped). Tests use `FakeExec`, which answers argv prefixes from recorded output in `src-tauri/testdata/maint/` and records every call (a report as `curl <url> --report`, a POST as `curl <url> --data <body>`); an `http` answer is 200 unless `coded(prefix, status)` gives the calls with that argv prefix another status (a 404, a 429, a redirect), `exiting(code, stderr)` gives every `tool` and `ssh` an exit and `without(bins)` takes bins off its PATH. Local git sources go through git.rs and are tested against `testutil::git` repos instead.
- **`TRUSTED_BINS` per cost class** is enforced inside `SysExec::tool`: `forge` may reach `gh`/`glab`, `tool` the audit binaries, `remote` `curl`/`ssh`. Argv is always an array; a value from data is a whole element and is refused when it starts with `-` or holds whitespace (`ssh_hostname`'s rule). A `tool` binary is resolved to an absolute file on the augmented PATH's absolute folders (`resolve_bin`) and that file is spawned, never the bare name: cmd.exe, and a bare name on Windows, look in the current folder first, which is the project, so a cloned repository's `npm.cmd` would otherwise run in npm's place. The child's PATH carries only those absolute folders (a relative or empty entry is the project) and it also gets `NoDefaultCurrentDirectoryInExePath=1`, so a shim's own `node` lookup skips the project too, and `noTool` is that same resolution failing. Two tools read the project before they read the lockfile, and each is pinned from outside it: on Windows npm gets `npm_config_prefix` set to its own shim's folder (`npm.cmd` runs `<prefix>\node_modules\npm\bin\npm-cli.js` when one exists, and a project `.npmrc` may name the prefix; env outranks it), and pnpm gets `--config.ignore-pnpmfile=true --config.manage-package-manager-versions=false` (`PNPM_SAFE`), since it loads `.pnpmfile.cjs` and switches to `packageManager`'s version, and only a CLI flag outranks a `pnpm-workspace.yaml` asking for either. Both are executed in tests against the real tool when it is installed.
- **`ssh` is the absolute file, the OS's own client first on Windows** (`ssh_bin`: `%SystemRoot%\System32\OpenSSH\ssh.exe`, whose agent service a GUI app can reach, then `resolve_bin`), run as `ssh_cmd`: `SSH_OPTS`, the alias, `sh -s`, the script on stdin through `run_fed`, which kills the tree at the cap. Each option is there for a reason and outranks the user's config, since ssh keeps the first value it gets: `BatchMode` (no prompt, so a key no agent holds is `noAccess`), `StrictHostKeyChecking=yes`, `UpdateHostKeys=no` and `CheckHostIP=no` (never a known_hosts write; the last adds an address whatever `StrictHostKeyChecking` says, and was on by default before OpenSSH 8.5), `ControlMaster=no` and `ControlPath=none` (no socket made, and none reused, so the transport is the same every time), `-a -x` and `ClearAllForwardings` (nothing forwarded), `PermitLocalCommand=no`, and `RemoteCommand=none` (a config's own would refuse our command). `the_ssh_options_are_ones_this_ssh_knows` executes `ssh -F <a hostile config> -G` against the real client, offline, because an old client refuses to start on an option it does not know. The alias is held to `deploy::ssh_alias` here as well as in `keep`.
- **A token goes on curl's stdin** (`-H @-`), never in argv. `HttpReq.auth` is `Auth::Env { head, name }` or `Auth::Sealed { kind, slot }`, built into curl by `http_cmd`, which a test drives with a stand-in opener. An env token is read only for a name on a fixed allowlist, and an absent one is `noAccess` *token not visible to Episko*, never *not configured*: a Finder-launched app gets none of `~/.zshrc`'s exports. No adapter reads one for a host a committed file chose, since an env token has no host (the `forge::glab` precedent). A **sealed** token (`maint_tokens.rs`) is checked by `sealed_ok` in `SysExec` before it is opened: only over https, only to a host (and port) whose own slot by the kind's fold (`maint_tokens::slot_at`) is exactly the token's, never a subdomain of it, never with a user or password in the URL, and only for a `forge` or `remote` read; `de.sentry.io` and `us.sentry.io` read with the `sentry.io` slot, no other `*.sentry.io` has one, and `sentry.io.evil.example` is its own host. curl runs with `-q` first, so no curlrc shapes a credentialed request (a `-v` there would print the header), and a failure's words have the header's credential taken out (`exec::redact`) before they reach a coverage, a trace's reason or a check. So a committed `sentry_url` picks among the slots the person saved and cannot steer a token anywhere else, and with none saved for its host the adapter asks nothing (`Exec::has_auth`) and says *no token*. `FakeExec` records a sealed request as `curl <url> --token <kind>@<slot>`, never a value, refuses it where `SysExec` would, and `without_tokens()` saves none.
- **Reads degrade, writes fail loudly.** `read` never panics into the IPC layer; a failing source never erases another's report (the `dep_report` rule).

**Registry contract tests** (cargo) run over every `SOURCES` row, so a new adapter inherits them:

- manifest source ids == `SOURCES` ids, unique and kebab-case; every facet has a source, a marker or a *none* phrase;
- a `FakeExec` answering `Err`, `""` and `"<html>"` never yields `Coverage::Ok`;
- `read`'s `Facts` kind belongs to the source's facet;
- in `mode: scan`, a counting `FakeExec` records zero calls for every `tool`/`remote` source and for `public` without the flag;
- every call a source makes uses only bins trusted for its cost.

**Findings → verbs.** A finding is `{root, facet, key, level, text, verb, source, ref}`. **One line per kind per project**, as *65 branches to tidy* is one line: every dependency advisory is one `security:dependency` line (*4 advisories*, its detail the severity mix and the packages worst first, deduped, three then `…`), and so are `code`, `config` and `secret` findings, each at its worst row's level with one verb whose brief (`patchBrief`, `codeBrief`, `rotateBrief`) covers every row behind it, each under its own heading with its package, installed and fixed version, id and link. One row still reads as it did (*high advisory* · *lodash · fixed in 4.17.21*). A count, and the mix under it, carries a `+` only for a kind a capped source reported rows of, so a capped Dependabot list leaves a secret read in full as *secret reported*. A brief is built from the same reports the line counted (`okFacts`: detected, not off, not skipped here), never from every report in the cache, and says so when one of them was capped. The key is the kind, so a verb outlives the rows coming and going under it, and `ref` is the kind. Failing CI is one `ci` line the same way: *CI failing 3d* for one workflow, *3 workflows failing* (oldest first, each with its age) for several, and `ciBrief` covers every red workflow under its own heading. Today's queue keeps a row per red workflow (`ciRows` reads `ciFailures`, not the line). A job that passed only on a re-run of its own commit is a line of its own, `ci:flaky` (amber; *build-check (windows-latest) passed on re-run 2×*, or *3 flaky jobs*), and lifts the CI cell to amber through `worseOf` (*1 flaky job*, *never ran · 1 flaky job*) while a red default branch stays red: *broken* and *noisy* are two lines with two briefs. Its *Fix* is `flakyBrief`, a different agent from `ciBrief`'s: find the nondeterminism in the logs and never add a retry, skip or quarantine. Today's queue never carries it (`ciRows` keeps a snapshot's red lines only), and a scan that read the re-runs but not the runs reached no CI verdict, so the last known red stands and Coverage lists the failed read (`vouched`). The Security cell says the mix rather than the worst alone: its two worst non-empty buckets (`sevMix`, short: *1 high · 3 med*, *1 secret · 2 critical*), coloured by the worst; an unknown severity is a bucket like any other and as loud as low, never the grey dot. *Fix* (CI, prod), *Patch* (advisory), *Rotate* (secret), *Upgrade* (a runtime past or near its end; `deps:packages`, every direct dependency a major or more behind, one info line whose brief lists them the most majors first), *Release*, *Plan deploy*, *Push*, *Tidy* (merged branches) prefill an agent via `host.launch` + `typeInto`, **with no newline** — the two places Episko presses Enter stay two. *Fix* answers several kinds, so its brief is the first row of `maintbrief.ts`'s `FIX`, an ordered `[test, brief]` table, whose test the finding's key passes: each test is exact (`ci`; `ci:flaky`; `release:deploy-failed`; a probe's `prod:<name>` and `prod:cert:<name>`; a domain's `prod:domain:<domain>`; the error tracker's `prod:errors:new`; `security:code` and `security:config`), so a new kind is one row and a key no row claims gets no brief rather than another kind's. The error tracker's *Fix* reads before it prefills: `maint_trace` asks the tracker for the latest event of the 5 worst issues on that click (their ids and the token are what leave; the verb's tip says so), and the brief gives each its exception and its project's own frames, innermost last, or says plainly why none was read; the trace is held for the brief alone. *Review* on bot PRs opens the existing `deps` overlay; *Fetch* (a stale last fetch) is `git_action(op:"fetch")`, and *Run* a `maint_read` in `explicit` mode, neither an agent; **A deploy is never Episko's to do.** `release:deploy` (*Plan deploy*, amber or info) is every production environment behind or off the trunk: *prod is 23 commits behind*, *prod runs 3 commits not on origin/main*, *2 environments behind*. `deployBrief` says what is live, what would ship and the `git log` ranges, sends the agent to how the project deploys, and ends on *Do not deploy, tag, push or trigger any workflow: a person ships it.* `release:deploy-failed` (*Fix*, red on production, amber on staging) is *prod deploy failed 2h ago*, and `deployFixBrief` reads the attempt's log and ends on `prodBrief`'s line: wait for a person before re-running, redeploying or rolling back. Both are prefills, so no third place presses Enter. A *Maintenance session* briefs several of these lines at once, each in its own tiled pane. *Set up* prefills a brief to add CI or an update bot (`briefFor` answers it for `ci` and `deps`), and, on a Coverage row rather than a finding, a code-scanning workflow where the forge offers code scanning and has it off (`coverSetups`, the brief keyed on `sec.code`: nothing is enabled on the remote); `[deploy]` is proposed from the Runs on card and project settings instead (`proposeDeploy`, slice 10).

## Surfaces

**Fleet.** A `segBtn` pair `data-flview` in `.fl-top` switches the body; both views paint `#fleetHead`/`#fleetBody` through the existing `paint()` guard, and `buildView` reads the `maintscan` cache only. The overview is one card per project (`fleetCards` joined by path for name, accent and group), worst first, seven cells, finding lines under a card with problems, quiet projects folded into one line, chips filtering. The head shows coverage tiles and *checked 4m ago · ⟳*. A cell click sets `maintSub` and `maintFilter` (fleetui module state, **not** a `mirror` field, so the thirteen mirror read sites are not touched; back/forward reads them through `fleetPlace` onto its own entry, docs/sessions.md) and opens Security / Delivery / Code / Servers / Work filtered to that project (`FACET_TAB`: ci, release → delivery; security, deps → security; git → code; prod → servers; work → work). Escape clears the filter before it leaves the stage. **Every card line is a door too** (`data-mtfind`): a click anywhere on it but its verb, or Enter on it focused, opens the same tab narrowed to the project and scrolled to the board that line summarises (`findingTarget`: an advisory line to the advisories, *1 update PR open* to the update pull requests, *CI failing* to the CI board, *10 commits since v0.37.0* to the release table, a hygiene line to the hygiene table, a work line to Work, a prod line to the addresses, a domain's line to the Domains board, a host's line to its card, and an errors line to the Errors board), or to the tab's top for a line no board carries; the verb still only prefills, and a severity picked on the strip is dropped so the rows the line counts are not hidden. A line looks clickable (cursor, hover) and stays as muted as it was; a snapshot's line opens the same way. A tab's head is a project picker (`data-mtpick`, the app's `./menu` popover): *All projects* or the chosen name, listing every project with what needs you there, red and amber only, those with something first (`projectPicks`); Escape still widens before it leaves. Each tab is built for its question rather than as a list of lines (*Tabs are boards* below). Overview's hosts get rows below the projects, joined many-to-many on `[deploy] host`, each one's tip no longer saying *not read yet* once the host answered (`HostRow.read`). A project not checked this session is drawn from its kept scan (`cc-maint-scan`) as it was, its sub *as of 3h ago*; one whose scan did not fit falls back to the `cc-maint` snapshot: `pastCells` makes every cell muted (`state: "past"`, a grey dot becomes *fine*), the sub says *as of 2d ago*, its lines carry no verb, and `projectBand` files it as *unread*, so neither the quiet fold nor the all-clear speaks for it and the tiles stay `—` until something is read; after that a zero tile over unread projects says *N projects not checked*, never *nothing broken*. The all-clear shows what was covered (`addCoverCaps`: the `sees` of what answered, and under *Not covered* every `blind` cap plus the `sees` of a source that failed or that nobody asked) and *coming up* (certificate, registration and EOL dates within 30 days).

**Scan progress.** A scan says what it is doing rather than only dimming. `./maintscan` keeps, per project, the reads a scan asked (`total`), those still out (`out`) and what holds one of the six slots right now (`live`: source ids, `DETECT` while `maint_detect` runs); `fleetProgress` and `projectProgress` read them through `./maintbadge`'s `scanProgress`. The fleet head draws a bar under its tiles (*3 of 31 projects done · 140 of 210+ sources read*, the `+` while a project is still detected, then what is read this moment and the share), a card being read draws the same bar as a hairline along its foot and its sub says *reading 4 of 9*, and a facet whose read holds a slot carries a spinner on its label, so the eye sees where the scan is working. The dashboard's tab draws one project's bar under its strip. The bar is a set width, never a looping animation, and `holdMaintPlace` starts a rebuilt bar where its predecessor stood so it glides; the spinner is `.u-spin`, which `fx-still` already replaces.

**The header chip.** Maintenance is two clicks deep, so the top bar carries a chip (`./maintpop`, `#mtBadge`), always drawn and as flat as a jobs-only pill until something needs you. It speaks for the project the stage is about (a session's, a dashboard's, a review's, a shelved or external session's), its seven facets as dots in card order (red, amber, grey for an answer, hollow for nothing read) and the count of its red and amber lines; with no project on the stage it counts the projects needing you, else those drifting, and is never the clear colour while one is unread. While a scan of that scope is out it is a spinner and *4/9* or *12/31*. A click opens a popover: the project's facets (each opens its sub-tab), up to five lines (each opens its sub-tab at its board, as a card line does), when it was checked and *Check*; then the fleet's tally and its worst projects, and *Open the Maintenance board*. Opening anything there goes through the dashboard's or the fleet's own door, so choosing the tab is the ask as before; the chip and the popover read the cache only, memoised on `maintGen`, which every change to the cache bumps.

**Every card explains itself.** A board, the sweep, Coverage, the Overview's cards, *Since last week* and the dashboard's three cards each carry an (i) (`data-mthelp`, probed first in `maintClick`) that opens `#mtGuide`, one popover over the stage: what the card answers, what it is read from, how to read its colours and what you can do there (`./maintguide`, markup only). *Read from* is never written by hand: it lists every manifest source whose `sees` meets the card's caps, grouped by when it is asked (every check from this machine or the forge, on a click, on *Check prod*), so a new source joins its card's guide without an edit and the module names no vendor. It closes on Escape, a click anywhere else, its (i) again, or a scroll, since the card it explains has then moved. A board's head is its icon (the guide's), a title, its note, and how it stands: a count of its red and amber rows as pills, the same colour down its left edge, so the eye finds the boards that need it before reading a row; a read board with nothing in it says *none open* with a check in its head and draws no body. A tab says what it answers in a line under its bar.

## Advisory sweep

*Does this advisory affect any of my projects?* The Security tab of the fleet carries one box: paste a CVE, GHSA, RUSTSEC or other OSV id, an advisory page's URL, `name@range` (`lodash@<4.17.21`, `@scope/pkg@^1.2`, `left-pad@*` for every version) or `ecosystem:name range` (`npm:next >=15.0.0 <15.5.6`, `cargo:smallvec <1.6.1`). Nothing runs until the person submits, the sweep is never part of a scan, and its runs are kept in memory for the session only (`maintscan`'s `sweeps`, at most six, newest first): no `cc-` key, no `localStorage`.

- **Two passes, the deterministic one first.** `sweep_advisory` (`maint_sweep.rs`) parses the query (`parse_query`: an id only for a known scheme prefix, so `left-pad` is never looked up; junk is refused with what would do) and resolves an id to its record at `api.osv.dev/v1/vulns/<id>` through the absolute curl as a `public` read. It is an explicit click, so it needs no per-machine opt-in, and the box says beside it what leaves the machine: **the id, and nothing else**. A record that names no package (a CVE converted from NVD often carries only a commit range) follows up to two of its aliases, GitHub's first, and those ids are all that is sent; `asked` lists every one. A package and range is built locally and sends nothing; with no ecosystem it is asked of every ecosystem `lockfile.rs` reads (npm and crates.io). A bare version typed there means that version in either: crates.io is not one of `deps.ts`'s caret-by-default ecosystems, since a sweep's range is a person's, not a manifest's. A record's own `versions` list is capped at 2000, and `versionsCut` says so: a version missing from a cut list is unsure.
- **Rust reads facts, TypeScript decides.** `sweep_match(roots, packages)` reads every project's lockfiles with `lockfile.rs` (read, never run, the same parsers `osv` uses) and answers per project the copies of each asked package (`found`: version and lockfile), the copies from git, a tarball, a path or another registry (`unpinned`, now named by `lockfile.rs` rather than only counted), a path or link copy (a `Cargo.lock` package with no source, a pnpm `link:`, a `package-lock.json` link: the project's own crate or package, or a vendored or `[patch]`ed copy, which a lockfile cannot tell apart) as unpinned too, the lockfiles read, and what might hold a copy and was not read (`unread`: a lockfile that failed or whose format version is not read, `yarn.lock`, `poetry.lock`, `go.sum` and the other lockfiles no parser exists for, or a manifest of any ecosystem — `package.json`, `Cargo.toml`, `pyproject.toml`, `requirements*.txt`, `go.mod`, `Gemfile`, `composer.json`, `pom.xml`, `build.gradle`, a `.csproj` — with no lockfile of its ecosystem in its folder or any above it), each with its ecosystem. Files are found at any depth through the project's index (`files::index_of`, the explorer's), plus `probe`'s root-and-one-level look for an ignored one; past 200 such files, or a cut index, every asked ecosystem gets an unread line, so a long list never reads as *not using*. npm names match exactly; crates.io and PyPI names fold case and `-`/`_`. npm names match exactly; crates.io and PyPI names fold case and `-`/`_`.
- **The verdict** (`sweepVerdict` in `maint.ts`, over `deps.ts`'s narrow `satisfies`): each OSV range run (`introduced` opens one, `fixed` or `last_affected` closes it; Rust splits the events) becomes a range string (`spanRange`), and each installed copy is placed (`placeVersion`). **affected** when any copy is inside a run (its evidence the lockfile, the version and the run; its fix the run's `fixed`, *bump → 4.17.21*, or *no fix published*); else **unsure** when anything could not be placed — a range shape `satisfies` answers `null` for, a version it cannot parse, a commit (`GIT`) range, a git or path copy, an unread lockfile of the advisory's ecosystem, a record naming no package — never a guess either way; else **patched** (*patched* when at or past a fix, *not in range* below where it was introduced); else **not using**, naming the lockfiles read. An unread lockfile of another ecosystem says nothing about this one. There is a row for every root asked: one `sweep_match` answered nothing for (cut at 500, or narrowed away) is unsure (*its lockfiles were not read*), and a failed read is the run's error, never an empty table. Rows are worst first, then by path.
- **The board** (`sweepHtml` in `maintview.ts`, fleet only, after the advisories): the advisory (id and aliases linking to its page, severity, every affected package and range), a verdicts table (project, verdict, evidence, fix) with the projects not using it named in one line below, and its doors, all `data-mtsweep`: *Patch* on an affected row prefills an agent on a fix branch with `sweepBrief` (the copies in range as advisory rows through the same `patchLines` the Patch verb uses, with `deps.ts`'s compatibility and verify blocks), never sent; *Check with an agent* on an unsure row runs `sweep_check`, `deploy::propose_toml`'s restricted headless agent (`claude -p --restricted --tools Read,Glob,Grep`, in that project) asked `sweepPrompt`, whose fenced `toml` block (`verdict` affected / not-affected / unsure, `evidence`) `parse_check` reads; the answer is shown in the row and changes nothing, so a row stays *unsure* and *Brief N agents* counts only the deterministic hits; *Brief N agents* prefills one agent per affected project, tiled on its own fix branch (*Maintenance session*); *Copy report* copies `sweepReport` through Tauri's clipboard; a recent run's chip shows it again. Enter in the box submits (`maintKey`), and the fleet's `paint` keeps the box's text, caret and focus across a repaint. Narrowed to one project, the table shows that project's row, and *Brief* and *Copy report* carry its root (`data-mtroot`) so they act on that row alone.

## Maintenance session

*Act on several findings at once.* Each card line on the fleet's Overview that an agent can act on wears a tick box, and *Brief N agents* in the action bar opens one agent pane per ticked line, tiled on the stage as one group, each with that line's brief typed in and never sent. The person reads each and presses Enter in each. The ticks are the fleet Overview's alone: the feature is about many repos at once, and a project's To do is one click away.

- **What can be ticked.** `VERB_KIND` classifies every `Verb`, a `Record`, so a new verb fails to compile until it says: `branch` (*Fix*, *Patch*, *Rotate*, *Upgrade*, *Set up*), `here` (*Push*, *Tidy*, *Draft release*, *Plan deploy*), or null (*Review*, *Fetch*, *Run*, no agent's work). `sessionKind` is what a line reads: its verb's answer, but `here` for a *Fix* whose brief changes nothing (`prod:*`, `release:deploy-failed`), and a suite holds that to the brief's own *Change nothing*. `prod:errors:new` is the one prod key that is code work: its brief asks for the cause to be found and fixed in the repository, so it runs on `maint/prod-errors-new` and its brief never says *Change nothing*, and its pane's brief reads the stack traces the verb would, or names why it could not. A suite holds every non-null verb to a brief that answers. A read still out (`busy`) cannot be ticked. A snapshot's lines are words rather than findings, and a quiet card is drawn compact, so neither has a tick.
- **`./pick`'s rule with Maintenance's own controls.** A click toggles, shift adds the range from the anchor in rank order and clears any text selection, an unpickable line in the range is left alone and `rangeOutcome`'s toast says so, Space or Enter on a focused tick toggles it. `cardsShown` is the one chip-and-fold filter, so the view and the range cannot disagree. `maintview.ts` draws `PICK_MARK` with `data-mttick` and `data-mtpicknone`, because it may not emit `data-dash*`. There is no header tick and no *All*: the cards are not a table, and a fleet-wide All would always pass the cap. A tick a chip hides still counts, and the bar says how many (*1 behind this filter*). A tick repaints the whole body, so the fleet's `paint` carries the scroller's place across it, within a tab: a new tab starts at its top. Every repaint of either host goes through `holdMaintPlace` (./dom): the keyboard returns to the same control's successor (by its `data-mt*`), or, when a keyboard-focused button became *checking…*, to whatever now stands where it stood, and a wide table keeps its sideways place per board.
- **Where a line runs** (`sessionPlan`). Code work gets a stable `maint/<line>` branch (`fixBranch`: `security:dependency` is `maint/security-dependency`) in a worktree off the trunk (`trunkOf`: the git read's, the release facet's, then `[maintenance] trunk`; with none, what the project has checked out, and the plan says so). An existing checkout on that branch is reused, so a second session lands beside the earlier work; one with a live agent in it, pane or external (`checkoutBusy`), is skipped rather than shared. A `maint/<line>` branch with no checkout is routine, since removing a worktree keeps a squash-merged branch (`branch -d` refuses it), and it is planned as what it is, an `old` row: `create_worktree` checks it out as it stands and ignores any base, so the bar says *earlier fix branch* and the brief tells the agent to read it and catch it up rather than claiming a fresh cut. A branch whose registered folder was deleted by hand is skipped and names `git worktree prune`, because git refuses it until then. A folder that is no git repo has no branch to cut, so its line runs in the folder, as that line's own verb does. *Push*, *Tidy*, *Draft release* and *Plan deploy* run in the project's folder with no branch: they work on the branches that exist or write nothing, and `maint/git-tidy` would be one more merged branch for *Tidy* to clear. So does a *Fix* that reads production and reports: it would leave an empty `maint/` branch, and a note saying to commit beside a brief saying to change nothing. A host's lines share one brief, which names everything the host has, so a second ticked line of one project's host is skipped with its reason (*another ticked line has this host's brief*). A path too long for Claude to file the conversation under (`worktreeDirLen` against `SLUG_MAX`, the handoff rule) and two lines landing on one branch are skipped with their reason.
- **Eight at most** (`SESSION_MAX`), one WebGL context per visible tile: visible tiles are exempt from eviction, so the cap is what keeps the pool under the webview's budget, and a contract test holds it equal to `terminal.ts`'s `GL_POOL_MAX`. It is a constant, not a threshold, since it judges no fact.
- **The bar says what a click makes** (`sessionText`: *3 selected · 2 on new fix branches · 1 in its project's folder*), and its tip lists each row's destination (`sessionTip`), and under a row whose brief reads stack traces first, what that sends and to whom (`traceAsk`, the line *Fix*'s own tip carries), so there is no confirm sheet. `sessionGate`'s reason is drawn as text, because a disabled button's tooltip is never reached: agents opening outside Episko, more than eight ticked, or the first skip's reason. Start is refused until that line is unticked: nothing is dropped behind the person's back.
- **Start re-plans.** The bar's plan reads `worktreesByRepo`, which can miss a project nothing else polled, so `startSession` drops lines that have vanished (*2 lines changed since the last check*, said in the toast the launch ends on), reads fresh `worktree_heads` and asks which fix branches exist, and plans again. Which branches exist is one `git_commit_info` per line, asked as a line is ticked so the bar can say *earlier* before the click, and asked again at Start, whose answer is the one the brief is written from. The bar can under-state a reuse and Start still cannot land in a busy checkout.
- **The launch** (`launchTogether` in `actions.ts`, the one place that touches `create_worktree` and `launch`; the fleet reaches it through `FleetHost.session`). One root's rows run in turn, since git holds a repo's worktree lock, and roots run in parallel, so tiles appear as their checkouts finish. `Sess.group.n` keeps them in ticked order however they finish. A failed worktree or launch is collected, the rest go on, and one toast ends it (`sessionDone`), the longer-lived kind when something failed or was left out. `starting` holds from the click until the last pane has landed, because a pane joins `sessions` only once its worktree exists and a second click any sooner would plan over the same checkouts; the ticks clear as the launch begins. A later member re-tiles only while a session holds the stage (`memberTakesStage`): leaving for the fleet keeps `stageGroup`, and a tile landing a moment later must not pull you back. No newline is written: each pane goes through `prefillFresh`, and a source-reading test fails if that path gains a `\r`, so the places Episko presses Enter stay two.
- **The note on the brief** (`branchNote`, for `new`, `old` and `wt` rows). The agent is told it is in a new checkout on `maint/x` cut from the trunk, to install the project's dependencies before the checks (a fresh worktree has none), and that it commits there while pushing and opening a pull request are a person's call. A reused checkout or an earlier branch is told to read `git log <base>..HEAD` first and to bring in what `git log HEAD..<base>` shows it has fallen behind. `create_worktree` tracks a remote base, so under `push.default=upstream` a bare push would reach the trunk; the note is what stands in the way until a no-track option exists.
- **The base is as old as the last fetch.** A session runs no `maint_read` and no fetch, so `from` says *as of the last fetch 9d ago* past `fetch_stale_days`, and *last fetch unknown* when no read carries one, rather than fetching.
- **Nothing persists.** `maintPicked` lives in memory like `maintSev`, with no `cc-` key, and `Sess.group` never reaches the roster: after a quit the members come back as separate shelved rows, as splits and run groups do.
- **The advisory sweep takes the same path** (`briefSweep`). *Brief N agents* and a row's *Patch* plan a `sweepLine` per project through `sessionPlan`, on `maint/<advisory id>` (or the package's name for a range with no id), so the cap, the reuse, the busy check and the note all hold. It has no ticks to untick, so `sweepGate` starts what it can and the closing toast names what it left out (`sessionLeft`: a project whose agent is already open), which also makes a second press after a partial launch pick up the rest. Past eight affected projects the button is disabled with the reason drawn beside it, and a row's *Patch* or a tab narrowed to one project still starts. With agents opening outside Episko there are no panes to tile, so each opens in its project's folder, as it did before this path.

## `[deploy]` and `[maintenance]`

```toml
[deploy]                                  # committed; proposed by an agent, written only after Apply
host = "prod-1"                           # an ssh alias; nothing connects until this machine allows it and a click
compose = ["api", "worker"]
urls = { app = "https://app.example.com", api = "https://api.example.com/health" }
sentry = "acme/api"                       # org/project; the token is never in the file
version_url = "https://api.example.com/version"
envs = { prod = "prod-*", staging = "staging" }  # environment → the tag, or a glob with * only, that marks what it runs

[maintenance]                             # optional; absent = detect everything
forge = "gitlab"                          # for a self-hosted host whose name says nothing
off = ["prod", "github-secret-scanning"]  # a facet ("not tracked") or a source id
sources = { ci = ["woodpecker"] }         # restrict a facet to these ids; detection must still agree
bots = ["acme-renovate"]                  # self-hosted update-bot logins
trunk = "dev"
tag_pattern = "v*"                        # glob_match (`*` only; ?, [ ] and \ are refused); which tags are releases
sarif = ["reports/*.sarif"]
[maintenance.params]                      # values a built-in source needs; a URL must be http(s)
woodpecker_server = "https://ci.example.com"
sentry_url = "https://sentry.acme.com"    # the error tracker, default https://sentry.io; https only, and it reads with the token saved for that host
sentry_environment = "production"         # one environment name; absent or empty: every environment, and the cell's tip says which
[maintenance.thresholds]                  # raw data; clampMaint applies them over the defaults
unreleased_commits = 30
unreleased_days = 21
stale_branch_days = 30
cert_warn_days = 21
bot_silent_days = 30                      # a configured bot whose newest open PR is older is *silent*
bot_pr_backlog = 5                        # open update PRs that count as a pile
fetch_stale_days = 7                      # release and git counts drift once the last fetch is older
eol_warn_days = 90                        # a runtime whose cycle ends sooner is drifting
flaky_reruns = 2                          # a job that passed on a re-run of its own commit this often in the window is flaky
deploy_behind_commits = 20                # production this far behind the trunk is drifting
deploy_behind_days = 14                   # or whose oldest undeployed commit is this old
deploy_idle_days = 180                    # no attempt for this long: listed, never judged
disk_warn_pct = 85                        # a filesystem this full is drifting, and at disk_bad_pct (95) broken
disk_bad_pct = 95
container_restarts = 5                    # a running container restarted this often is drifting
load_per_cpu = 2                          # the 15-minute load per CPU that is drifting
domain_warn_days = 30                     # a registration ending sooner is drifting: renewing one often needs a person with a card
new_errors = 1                            # unresolved issues new since the last release, regressed or escalating, that make Prod drifting
error_users = 100                         # one of them reaching this many users, or any fatal one, makes it broken
```

- A red default branch is broken from its first failing run, however young: CI has no threshold. Every threshold is `MAINT_DEFAULTS` until the file says otherwise, and a stale fetch lifts a Git or Release cell to drifting with its own `git:fetch` finding, so amber always has a line under it. Two cells keep that rule by judging what their lines judge: a local-only branch is the Git cell's tip and an *info* count on the hygiene board, never its amber, since with nothing unpushed a remote holds every commit it has (a fresh session worktree's branch, the checked-out branch before its first push); and the update-PR backlog is one bot's pile, as each bot's line and board row are, never the sum across bots.
- Read forgivingly, by every owner's own `RawFile` that ignores other tables. A file that exists and does not parse is `readable: false`, and the tips say *episko.toml unreadable* rather than quietly applying defaults (`ProtectList.readable`'s rule).
- `[deploy]` is written only by `write_deploy`: `toml_edit` read-modify-write, tmp file then rename, only the keys whose value changed replaced (a hand-written value keeps its comment), compared against the table as the reader saw it, so a key whose only difference is a value the read dropped is left alone, and a rewritten `urls`, `envs` or `compose` is edited in place: only a shown entry the proposal left out goes, and an entry the read dropped, refused or of the wrong type, stays with its formatting (the proposal never saw it, so it cannot mean to remove it); a `urls` list becomes a table, no write when unchanged (the file is committed and churn lands in a diff), the table removed when empty, `create` gating a new file. A missing file with `create: false` is refused with `NO_FILE`, and `proposeDeploy` then asks *Create .episko/episko.toml?* before writing it: Apply answered for the table, not for a new file. Reads drop an unsafe value (a host that is not an ssh alias, a service that is not one argv word, a non-http address, a `sentry` that is not `org/project`, a `urls` name holding `:`, an `envs` name that is empty, over 64 characters or holds a control character, since it reaches a prefilled brief, or a pattern that is not a `*`-only tag glob); the write refuses it and names it. A host is `[A-Za-z0-9._@-]` with an alphanumeric first character (`ssh_alias`, deploy.ts's `isAlias`), tighter than one argv word because it reaches a brief and, from a later slice's host card, a shell prefill, where `;`, `$(` or a backtick is a command. `compose` names the services expected on that host, matched on the Compose `service` label, every replica counted, and a table that only names a host is read, not a `[deploy]` marker. A url's name is its finding's key after `prod:` (`prod:app`, `prod:cert:app`), and every other prod source keys its findings `prod:<kind>:…` (`prod:host:disk`, `prod:domain:<d>`, `prod:errors:new`), so with no `:` in a name the two can never collide; a bare list's address is named by what follows its scheme with a port's `:` as a space (`localhost 8080/up`). A write that changed the file drops Rust's detection for the project (`forget_detection`) and the cached reports of every source whose manifest `needs` names `deploy.` (`forget_deploy_reads`; `http-probe`, `rdap-domain`, `ssh-host`, `sentry-issues` and `deploy-tags` today), so the rescan that follows offers *Check prod* again rather than the old addresses' answers, and every other report stays. It is reached from the Apply dialog after `propose_deploy` (the restricted headless agent `propose_stack` uses, through the shared `propose_toml`; `checkDeploy` refuses non-http URLs, a url name holding `:`, a host that is no ssh alias, a bad `org/project` and a bad `envs` name or glob), or by hand through *Open file*.
- A table holding a key a prod source would read (`host`, `urls`, `version_url`, `sentry`) with no prod source reading it is a `[deploy]` marker, so the Prod cell says *can't check ([deploy])* rather than *no deploy*. `envs` or `compose` alone name no address, so a project that only tags its deploys says *no deploy* there.
- `[maintenance]` is set up the same way, for four keys only: `trunk`, `tag_pattern`, `sarif` and `bots` (`MaintSetup`, `deny_unknown_fields`). `off`, `sources`, `forge`, the thresholds and the params change what is read or judged and stay a person's, so the proposal lists any other key it set as left out, and the writer never sees one. `write_maint` goes through `edit_toml` with `write_deploy`'s rules (only a changed key replaced, no write when unchanged, `create` gating a new file), but a write that changed the file drops the project's cached reports too, the bots' PR read with them: every one of the four keys feeds a cached read, and a rescan that served the old reason would make Apply look like it did nothing. It refuses a trunk that is not one argv word, holds `* ? [ ] \ ~ ^ :` or is a revision expression (`@{`, `..`, `@`, `HEAD`), a tag pattern with any wildcard but `*`, a SARIF path that leaves the project (`sarif_inside`, the rule `sarif-files` walks by) and a bot that is not a login, naming each. A table left with only `[maintenance.thresholds]` keeps no empty header, unless a comment rides on it, and an unchanged setup never touches the header. `maintPrompt` shows the agent the current keys and every Coverage reason a key would answer (*no remote, so no default branch: set [maintenance] trunk*), and `maintCfgText` names each current value the proposal changes or removes. The doors: *Propose with an agent* and *Open file* on the project tab's Coverage rows whose reason names a key (`setupKeyOf`; a read whose gap names one, as `git-local`'s merged branches without a trunk, says so on its row), and the project settings panel's **Maintenance** row beside **Where it runs**. `test/fixtures/maint-checks.json` is run by both `keep_setup` and `checkMaintCfg`; its `key` lines are `checkMaintCfg`'s alone (Rust names the key in `unknown`, and serde refuses it at write). maint.test.ts holds `SETUP_KEYS` to maint.rs's.
- `deploy_config` and `write_deploy` resolve a project path to the repo root (`root_key`) exactly as detection does, so a subfolder project or a worktree reads and writes the main checkout's file, the one the Runs-on card reads. Every *Open file* for `[deploy]` or `[maintenance]` (project settings, the Runs on card, Coverage) and the create prompt ask `episko_toml_path` for that file rather than building `<project>/.episko/episko.toml`; `[stack]`'s *Open file* keeps the project's own, since `stack.rs` reads the path as given. A Re-check shows the agent the current table verbatim (`deployToml`), since a value it is not shown is a value it drops and Apply would remove; the dialog lists each current value the proposal removes or changes (`deployLosses`). `test/fixtures/deploy-checks.json` is one case table run through both `keep` and `checkDeploy`, so the two refusals cannot drift.
- A round-trip test writes `[deploy]` and `[maintenance]` into a file holding every other table and runs `parse_stack`, `parse_protect`, `parse_allow` and `parse_health_policy` over it.
- Config lives in git and never in sync: it changes what runs (`docs/stack.md`).

## Adding an adapter

1. Add a row to `src/maintmanifest.json` (facet, label, cost, forge, detect, sees, blind); if it was a marker, delete the marker.
2. Write `read_x(ctx, ex) -> Result<Read, Coverage>` in the facet's `maint_*.rs`, using only `Exec`. Map stderr to a coverage with a `fix` when one exists. A non-zero exit from an audit tool is data (`run_capped`'s rule).
3. Add the `SourceDef` row. A new binary goes into `TRUSTED_BINS` under its cost class, and a new `tool` binary is a design review item.
4. Record a real output in `src-tauri/testdata/maint/` and test the parser and `read` over `FakeExec`. The registry contract tests apply on their own.
5. Only if the facts fit no existing `Facts` kind: add the variant on both sides, regenerate the wire fixture, teach `facetCell`/`findings`, test it. Otherwise nothing changes in TypeScript.
6. A new capability goes into `MAINT_CAPS` and its Rust mirror; a new env token onto the allowlist.
7. Add a row to the adapter table below: what it reads, its cost, its credential, what leaves the machine.

A filtered `total_count` stops at 2500 whatever the window holds, so it decides how many pages to ask and is never stated as a count. The page size is spelled out because `gh --paginate` asks 100 unless told, and 100 answers 502 on a big run (vercel/next.js) where 30 answers; a run too big for `gh`'s 60s is a gap. A `run_attempt` above 1 is not yet a re-run: approving a fork's workflows also makes attempt 2, with no job in attempt 1 (tauri-apps/tauri), so `reran` counts the runs whose jobs show two attempts. A failure begun only once every failure begun before it had ended is an aggregate gate (`if: always()`, apache/airflow's *CI passed*) and is not counted: it fails because the others did, so it would collect every other job's flakes and reach the threshold first. The jobs API has no `needs`, so the times are the only trace; a job that merely started late in a run with another failure is a missed flake, the cheaper error. Folded per workflow and job, only the jobs that passed at least once, at most 30, each with its failing steps (most often first, ≤ 3) and its newest 3 occurrences. A finished attempt's jobs never change, so they are kept in memory per (repository, run, attempt count). The unit is the **job**: GitHub has no test-result API and a failed job's annotations carry no test name (episko's flake says only *exit code 1*), so the step is the finest grain read, `ci.per-test` is blind, and the brief sends the agent to the log. A failed page 1 is `gh_coverage`; a later page or one run's jobs that fails is a gap with `truncated`, never the coverage. Both jq filters hold no double quote, and `gh` runs with no shell. The bounds start low on purpose: the CI cell waits on this read, so raise them only after measuring a fleet's scan |

Every other row is a marker in `src/maintmanifest.json` until its slice promotes it. `sarif-files` and `http-probe` have none: they read what config names rather than what is on disk. **`forge-commit-status` detects the config files of the CIs that report back** (`Jenkinsfile`, `.circleci/config.yml`, `.woodpecker*`…) rather than nothing: an empty `detect` would make it a source on every GitHub repo, and step 3's *no CI* could never be drawn. On GitHub those files are its, so their markers say `"forge": ["!github"]`; `no_marker_claims_a_file_a_source_reads` holds a marker off any file a source of its facet reads on the same forge.

Every GitLab read runs as whoever glab holds for that host (glab has no per-call account the way `GH_TOKEN` gives gh one, so `Ctx.account` is not passed). `classify_glab` turns its failures into coverages, every fix `glab auth login --hostname <host>`: glab missing is `noTool` with its install link, signed out (a 401, an invalid token, glab asking for `glab auth login`) is `noTool`, a 404 (GitLab answers a project an account may not see exactly like one that does not exist) or a 403 (`insufficient_scope` included) is `noAccess`, a rate limit and anything else is `error` verbatim. A pinned GitLab host is read, unlike a pinned GitHub one: a self-hosted GitLab is the reason the pin exists. That is why `forge::glab` removes `GITLAB_TOKEN`, `GITLAB_ACCESS_TOKEN`, `OAUTH_TOKEN` and glab's CI variables from its child: glab sends an env token to whatever `--hostname` names, ahead of its per-host login, and the host comes from the repository.

Every GitHub read runs as the project's pinned account (`Ctx.account`, the `gh` `account` the frontend passes). `gh_coverage` turns its failures into coverages: gh missing or signed out is `noTool` with its fix, a 404 / *could not resolve to a repository* / any 403 but a rate limit (SAML SSO and fine-grained tokens included, checked before `classify`, whose *token* match would say `gh auth login`) is `noAccess` naming who asked, a pin gh no longer holds is `noAccess` with `gh auth login`, anything else is `error` verbatim. A host pinned as `github` that is not github.com is `unsupported`, since the same `owner/repo` there could be someone else's; a pin the host table agrees with (an ssh alias that resolves to github.com) is reported `by: table`, so it is read.

The trunk is `[maintenance] trunk` when it resolves to a commit (a typo is reported, never replaced by `main`), else the primary remote's default branch (origin, else the first remote; the forge is read from the same one). There is no local guess: a repo with no remote and no pinned trunk gets the tip *set [maintenance] trunk*.
