# Reviewing a pull request

> Rules and their reasons, compressed. Trust the code over the docs when they disagree, and fix the doc in the same commit.

A stage of its own (`takeStage("review")`, `mirror.kind === "review"`), opened from a PR in the project's queue (⊞), from the PR reader (*⊞ Review changes*), or by a MOD-click on a github.com PR link in any pane (`openPrLink`, `cc-pr-links`). That last one opens here only when a known project's `origin` is that repo (the clicking pane's project first, then every open session's, then the favourites); otherwise it goes to the browser, so a fork whose `origin` is not the PR's repo still does. `review.rs` reads and writes GitHub, `review.ts` decides, `reviewview.ts` draws and `reviewui.ts` owns the pane. The diff itself is the working-set viewer's: `diff.ts` parses it and `patchview.ts` draws it, extended with per-line hooks rather than forked.

- **A review you open gets a row in the sidebar until you close it** (`cc-review-open`, local, at most 12). The row sits under the ⑃ checkout on the PR's head branch (`reviewCheckout`; never for a fork's PR, whose branch name means another repo), else under the project, and it holds that checkout's cluster open the way a shelved row does. Leaving the stage any other way keeps the row, and coming back to the **same** PR keeps the module's state (tab, folds, scroll, the text being written) and only re-reads GitHub quietly. Another PR starts afresh: `reviewui.ts` holds one review at a time. ✕ and Esc *close* the review, which drops the row; the row's own ✕ does the same from anywhere.
- **GitHub's diff is the one every comment is anchored to: merge base → head, three dots.** A review comment names a `path`, a `side` (`LEFT` = the base's numbering, `RIGHT` = head's) and a `line` (`start_line` for a range). That is GitHub's REST contract, and VS Code's extension uses the same. `position` is deprecated and never sent. The local diff only lines up with GitHub's because `pr_diff` diffs `base_oid...head_oid` with the same oids GitHub reported, so the numbers are the same numbers. **A line outside every hunk is refused with a 422**, and a range may not cross two hunks. `commentableIn`/`canComment` encode that, so the `+` is only drawn where GitHub will take it, and a shift-click across hunks says why and does nothing.
- **Other views are for reading.** *Since your review* (`from = the head your last submitted review saw`, read from GitHub's reviews rather than stored here) and *one commit* are two-dot diffs. Their old side is not the base, so `liveSides` keeps `LEFT` comments out of them, and a commit that is not the head takes none at all. Threads whose side the view does not share are drawn at the file's head, never on a row that happens to have the same number. Hiding whitespace swaps the drawn diff but not `commentable`, which is always measured on the real one.
- **The pending review lives on this machine until Submit, then goes in one call.** `cc-review-drafts` (local, never synced), one `POST …/reviews` with the verdict and every line comment. File-level comments cannot ride a review (the endpoint has no `subject_type`), so `review.rs` posts them right after it. No GitHub-side pending review exists, so nothing half-sent is ever visible to the author.
- **Viewed undoes itself when the file changes.** The tick stores `fileSig`, a hash of the file's part of GitHub's diff, so a push that touches the file clears it and one that does not leaves it. It is measured on the diff as read, never on context revealed into it. One exception: a file that crosses the review's cap (whole ↔ *not loaded*, below) is signed afresh, so its tick clears though the push did not touch it. Viewed files open folded. The rail ticks it too, on every file row and, in the tree, on every folder row: a folder's tick covers its whole subtree, shut subfolders included, reads as a dash part-way, and takes the rest when clicked there. A rail tick moves the stream only when it folds the file you are in, and unticking a folder leaves its folds, since opening them all is what a large view exists to avoid.
- **Merging carries the head you reviewed.** `pr_merge` sends `sha: head_oid`, so GitHub refuses if anybody pushed since the page read it. `mergeBlock` refuses only what GitHub certainly would (draft, conflicts, nothing allowed). Everything softer (`BLOCKED`, failing or running checks) is a warning in the confirm, because an admin may merge anyway and GitHub has the last word. The branch is deleted through the API, never `gh pr merge --delete-branch`, which switches the local checkout. Deleting it is **off until you tick it** in the merge menu, since a PR's head is often a long-lived `dev`, and even then `pr_merge` keeps a branch that is the default, a fork's, locked in `.episko/episko.toml`, or the base of another open PR (GitHub itself refuses one its protection guards).
- **`pr_diff` fetches without writing a ref.** Missing commits are fetched by oid (then `refs/pull/N/head`) with `--no-write-fetch-head`. The user's repo gains objects and nothing else (the CLAUDE.md rule on writing outside our storage).
- **Feedback goes to an agent as a prefill, never a send.** *→ agent* on a thread, on the pending comments or *❯ Session* in the head prefills `agentBrief` into a session on the PR's branch: a live one if there is one, else one launched in that branch's worktree, created from `origin/<branch>` (after one fetch if it has never been fetched). A fork's branch is not checked out for you. The reviewer reads, edits and presses Enter: this is not one of the two places Episko presses Enter.
- **The file rail is a tree or a flat list (`cc-diff-tree`, shared with the working-set viewer).** Both layouts and the stream use `treeOrder`, a folder's own files before its subfolders, so the three never disagree about what comes next. A chain of single-folder folders is one row, as VS Code draws it.
- **A large pull request is drawn a file at a time, and only past `LARGE_ROWS`** (10,000 diff rows over the view's files, `isLargeDiff`, decided per view in `loadDiffs`). Below it nothing changes: a fold is a class toggle, *expand all* is there, and a review opens unfolded up to 60 files. Past it every file opens folded each time you arrive at the view (a range, the whitespace switch, a push; ⟳ keeps what you opened), a folded file is its header alone (`FileActs.bodyless`), opening one draws its body through the per-file repaint a comment already uses, folding puts it away, and the bar offers *collapse all* but never *expand all*. Lazy per file rather than virtualised by viewport, because the sticky headers, the rail's scroll spy and `keepPlace` each need every header in the DOM; headers are cheap and bodies are what cost. `pr_diff` has its own cap (`REVIEW_PATCH_CAP`, 16 MB, not the working set's 800 KB) and never cuts inside a file: files load whole in git's order while they fit, the rest arrive as `Diff not loaded: +A -R` stubs (`DiffFile.cut`), so every file is listed and counted, the bar says how many were not loaded, and the note sits above the first file. Only when even the stubs do not fit (tens of thousands of files) are the last ones left out; the backend counts them (`PrDiff.dropped`, never inferred from GitHub's file count, which git's rename detection need not match) and the Files tab reads *N of M*. GitHub sends the newest 100 commits only: the head says `commit_count`, a commit is numbered in the whole PR (*Commit 160 of 162*), the menu says *latest 100 of 162*, a commit diffs against its own `parent`, and a review older than the list reads *100+ new commits*, unless a force-push followed the review (`forced_at`), which still reads *rewritten*.
- **Typed text is state, not DOM.** Every repaint (a thread landing, a range switch) rebuilds markup, so the comment being written, each reply and the conversation box are mirrored into module state on `input` and painted back. The summary lives in a static textarea in `index.html` for the same reason.

**Not here, deliberately:** applying or committing suggestions (that writes to someone else's branch from the reviewer's seat, and *→ agent* does it with tests run), reactions, editing or deleting sent comments, reviewers/labels/milestones, CODEOWNERS (the `review_decision` GitHub already computed is shown instead), re-running CI, rich diffs, live updates (⟳ and *since your review* cover it). docs/dashboard.md has the queue that opens this.
