# Releases & the changelog

> Rules and their reasons, compressed. The full narratives live in git history (CLAUDE.md before the split). Trust the code over the docs when they disagree, and fix the doc in the same commit.

`CHANGELOG.md` is the only place release notes are written, with three consumers that must never disagree: the app's *What's new* (`changelog.ts` → `changelogui.ts`), `release.yml` (lifts the tag's section into the release body), and `ci.yml` (refuses a dev→main PR whose `## Unreleased` is empty).

- **The app ships the file** (`?raw` import), never fetches it, so a build can only ever describe itself.
- **The gate is on the PR rather than the tag**, because a failed tag has the ship decision already behind it. `pnpm changelog draft` writes the section through Haiku and **stops** (never commits); the gate checks only non-empty, never that a model wrote it.
- **Three markers, not six headings**: `+` new, `~` changed, `!` fixed.
- **A section with no entries and no lede is dropped at parse time**: `changelog release` opens a fresh empty `## Unreleased`, so every released build ships one; kept, it rendered a "next" row that opened on nothing. The branch policy stays enforced by `changelog.mjs check`, which has its own parser.
- **`inlineMd`'s ordering is load-bearing**: bold runs first and must tolerate a `*` inside it; italic runs *inside* bold's output, anchored on a `*`-free run so `2 * 3` is left alone. It lives in `changelog.ts` rather than the DOM module, so it is tested; where it used to live, the missing italic rule went unnoticed for nine releases. The lede goes through it too.
- **`shouldAnnounce` opens once per released version**; `cc-seen-versions` is a set (the legacy single-value `cc-seen-version` is folded in once); a build with no section (a dev build) is silent.
- **Don't reintroduce the fresh-install guard.** It keyed on the seen-record being absent, which is exactly every install's state on the release that *introduces* the record, which is why 0.13.0 shipped silent. Any "does localStorage look used" rescue is measured wrong (`cc-icons`/`cc-restore` are written during first boot, before `changelogui` imports) and untestable (import-order dependent). The cost of living without it: a first-time user sees their installed version's notes once.
- **The release body is assembled in a workflow step rather than inlined YAML**: a multi-line `${{ }}` in a literal block mangles indentation; the install text lives in `.github/release-install.md` and is concatenated.
- A tag with no matching section still releases (the notes say so); failing after the ship decision just moves the problem.

## Preview builds

A push to the `preview` branch builds a **preview**: `preview.yml` replaces one prerelease, tagged `preview-build`, with a build of that commit. It exists to try a feature in the running app before it ships. *Settings › Updates* switches between the two channels, and installing either build by hand works too.

- **It can never reach a stable user.** The stable updater and the site read `releases/latest`, which is never a prerelease; the job fails if `releases/latest` stops being a `v*` tag; `site.yml` skips a prerelease event, and its stamp script filters them out.
- **Same identifier as stable**, so it installs over the installed Episko and runs on the same data. Going back is a downgrade to the latest release, which NSIS and a `.dmg` both allow.
- **The switch is the updater pointed somewhere else** (`updates.rs`), because the plugin's own `check` reads only the endpoint the config names. `cc-update-channel` holds the choice and is `shared`, or a preview going back would leave stable asking for the preview again; with no choice made, a build is on its own channel. On the preview channel both manifests are read and the newer wins, so a release that overtakes the preview still arrives. Entering a preview needs one newer than the build; leaving one takes the latest release whatever its version. What is found goes into the webview's resource table as the plugin's own check would put it, so the plugin downloads, verifies and installs it. Both endpoints are constants that a test holds against the two configs. An `.msi` install switching to a preview gets the NSIS build installed beside it, since there is no `.msi` to take.
- **The version is the next patch with `-preview.<run>`**, so a preview updates the last one, and it is stamped into `tauri.preview.conf.json` in CI so tauri-action writes the same version into `latest.json`. That overlay also points the updater at the prerelease. **Windows builds NSIS only**: an `.msi` refuses a pre-release that is not numeric.
- **A preview keeps its settings to itself, so stable needs no code to survive one.** Built with `VITE_EPISKO_CHANNEL=preview`, it reads and writes every `own` key in `src/channel.ts` under a `preview:` prefix, falling back to stable's value until it writes its own (a removal leaves a marker, or stable's value would show through again). Everything a return to stable must find (spend, sessions, notes, accounts, projects, sync's books) is `shared`: one copy, written through. `test/channel.test.ts` holds every key in exactly one list, and every synced pref in `own`.
- **A preview may add keys; it must never change the shape of a `shared` one.** Stable reads it after the downgrade, and a value it cannot narrow is dropped. The same holds for `.episko/episko.toml`: a new table survives stable (read by name, written through `toml_edit`), a reshaped one does not.
- **The hook is `main.ts`'s first import** (`channelhook.ts`, held by the test): `state.ts` reads keys at module scope, and synclink's write hook must wrap this one. A preview sends none of its own settings to other machines; what arrives is held for review as everywhere else and, accepted, lands in the preview's copy. A stable build patches nothing.
- **`cc-channel`** records which channel last ran here and since when. The first run of the other channel asks once, and only about the settings the preview kept a value of its own for that differs from stable's (`differing`): back on stable, whether to bring them along (`adopt`, which syncs them like any change); in a preview, whether to read stable's again (`drop`). Either answer reloads the interface, since `state.ts` read every setting at startup. A switch with nothing to decide asks nothing.
- **`preview` is an integration branch**: the feature under test merged with whatever the preview machinery needs that `dev` does not have yet. A push trigger runs the workflow file of the pushed commit, so `preview.yml` must be on the branch. Pointing it at another feature is a reset and a force-push, which is the user's to do.
- `VITE_EPISKO_CHANNEL=preview pnpm tauri dev` runs the hook locally. The dev server is its own origin, so it has its own localStorage either way.
