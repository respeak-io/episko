# Architecture deep dives: backend & frontend

> Rules and their reasons, compressed. The full narratives live in git history (CLAUDE.md before the split). Trust the code over the docs when they disagree, and fix the doc in the same commit.

## AppState & the disk-I/O accounting

`AppState` holds the telemetry `port`, the `sessions` map (PTY master + writer + child killer each), `agent_runtimes` (provider sidecar child + control channel), `owned_pids`, `io_samples` (previous per-pid reading → the inspector's rate), `io_retired` (bytes of exited sessions, so the total doesn't fall on close), the held-open Claude `pending` permission requests, and `caffeinate`.

**Both I/O fields are in-memory, so `all_sessions_resources` reports a *run* figure, which is why `cc-io` exists.** `addIo` banks each poll's increment into a per-day rollup off the same sample the live bars use; `ioDelta` clamps a drop to zero (a restart is the normal case, the same reasoning as `costDelta`). No back-fill: missing days are "not recorded", never zero, and `ioTotal()` answers **null** rather than `{r:0,w:0}`.

**The three windows (run/today/all) genuinely coincide at first** (one recorded day; a run's first poll banks the whole counter), which reads as a cycling control that does nothing. `ioSameNote` (pure, tested) names the coincidence and returns null on divergence; it compares the **rendered** strings rather than floats. The `⟳` beside the label is the affordance.

**The write is floored at a minute**: the poll runs every 4s while a session is on stage; persisting each reading would be ~900 writes/hour for a number read daily. Accumulation is per-poll (free); only `flushIo` writes, forced across midnight and on `quit-requested`. Skipping polls loses no bytes (cumulative counters + `io_retired`); the one real loss is the stretch after the last reading (`flushIo` persists, it does not sample).

**What a gap costs is the day the bytes are filed under**: buckets are credited when the poll *lands*, and the poll is gated three ways (`mirror`, on-stage, background-webview throttling), so a quiet stretch over midnight booked a whole evening's churn to the next morning, wrong in both directions. Two halves fix it, both needed: **`splitIo`** (pure, tested) spreads an increment over its window weighted by each day's wall-clock share (a bounded, unbiased guess whose parts sum exactly, clamping windows no polling gap explains) and a **60s heartbeat** in `main.ts` calls `pollIo` (a pure counter read; `refreshSessionStats` no longer spawns anything, since the working set comes from `dirtyByFolder`). The cadence is `IO_SAVE_FLOOR_MS` exactly, so the heartbeat cannot raise the write rate, and `addIo` returns early when the disk was idle. **A meter must not add to what it measures**, so keep any new sampler on that footing.

**Be honest about coverage**: the counters cover the `claude` processes only, nothing they spawn (verified: a child's 64MB write moves the parent's `proc_pid_rusage` by 0.0MB), so `cargo`, `pnpm`, `git` and test runs are invisible, so real churn is *higher* than shown. Expect physical writes at several times the logical bytes (APFS is copy-on-write and transcripts grow by small appends).

**A Claude Code self-update is discounted, because it is the one figure here that was pure noise.** The native installer writes a whole new ~290 MiB binary into `~/.local/share/claude/versions/`, and the process doing it is a session of ours, so the kernel charges every byte to a `claude` pid the meter sums: the day read as ~300 MiB of agent churn — thirty times a hard day's real work — in the *first minute*, on the first launch after a few days away, i.e. the number a returning user sees first. Measured 2026-08-16: `2.1.233` = 292.8 MiB written by the session's own pid, whose counter then sat still, while Episko's process wrote 0.8 MiB; the two earlier spike days in the rollup match `2.1.232` and `2.1.227` byte-for-byte, each with a *tiny* read figure, since the bytes arrive over the network. An info-panel bullet was the alternative and is not enough — nobody reads one to find out whether a number means anything.

The mechanism, split so the decision is testable: `all_sessions_resources` reports `install` (name + MiB per installed binary, one `read_dir`, no contents; the directory is resolved **once per run** in a `OnceLock` because `resolve_claude()` can end in a login-shell probe and this runs every 4s), and `installGrown`/`addIo` in `usage.ts` own what it means. **Evidence, never a threshold**: a "reject the implausibly large window" rule would also swallow the runaway agent this meter exists to show, and could never say which it had done. Four properties hold it together — the first reading is a baseline only (what was installed before the run was never charged to us); *growth* counts as well as arrival (a file written in place spans polls) while a pruned version credits nothing; the credit is spent against this window's increment **and then against the day already banked**, because the flush and the directory entry need not land in the same window in either order; and it can never give back more than this run reported, so a foreign update (a `claude` in a terminal) cannot eat a real day, with anything unclaimed expiring after 10 minutes rather than standing as a discount against whatever writes next. `ioCreditBps` takes the same bytes out of the *rate* off the same sample. Two known edges, both deliberate: an update banked before midnight and discovered after it leaves yesterday alone (stage two only reaches today), and an npm/Homebrew install has no versions dir, so the list is empty and every figure is raw — correct, since a package manager's writes are charged to itself.

## Provider control planes: one cockpit, several transports

`Sess.kind` describes the product object (`agent`, `shell`, `task`); it does not encode a vendor. Every agent carries `provider` and a copied capability list, so a session stays self-describing even if the installed-agent catalogue refreshes or its observer disconnects. Shared UI code asks for `session-state`, `activity`, `context`, `usage`, `permissions`, `launch-permissions`, `resume`, `history` or `external-terminal`. Vendor checks are reserved for the launch/protocol boundary.

Claude keeps its hook/statusLine transport. Codex starts one loopback [App Server](https://developers.openai.com/codex/app-server/) per pane in `agent.rs`; Episko and the real `codex --remote` TUI are two clients of that server. The observer claims the first top-level thread in the pane's exact workdir, subscribes with `thread/resume`, and forwards that thread plus its registered descendants and account notifications. Descendant payloads are tagged so the adapter keeps their tools/files/approvals but not lifecycle or plan state. Approval requests use opaque ids and a shared FIFO, so overlapping parent/child requests are not overwritten. Closing the PTY stops the observer and sidecar. History uses App Server's stdio JSONL mode (`thread/list` / `thread/read`) rather than reading Codex's private rollout database. The WebSocket transport is currently experimental in Codex, so keep this boundary isolated and verify generated schemas when upgrading the supported CLI.

The frontend boundary is deliberately two-stage. `providers/codex.ts` knows vendor method and item shapes and returns a small `AgentEvent` vocabulary; `agents.ts` is the only shared reducer and drives the same phase, attention, activity, file/context, approval and usage fields that Claude's reducer drives. Codex cost is an API-equivalent estimate from App Server's cumulative USD figure or, when that route is absent, its per-model usage groups at standard public API rates. The footer follows the active integrated agent and names that provider; quota snapshots are shared only between panes carrying the same non-null opaque account scope, while Claude's adapter retains its account-wide burn forecast. `providers/index.ts`, `providers/manifest.json` and `docs/providers.md` define the extension contract for additional integrated agents.

An OpenCode integration should follow that seam: add a backend transport, a provider adapter, and only the capability flags its structured API can uphold. Until then it remains terminal-only. Do not infer state from terminal text; a vendor TUI redesign would silently turn trusted status into fiction.

## The `innerHTML` guards on `renderAll`'s path

The pattern: build the markup every pass, assign only when the string differs from the last write. Guarded: `renderSidebar` (`#projects`), `renderMini` (`#railmini`), `renderInspector` (`#inspector`); `updateTray` diffs a signature; `dashboard.ts`'s `paint(id, html)` per surface. `syncStageButtons`/`reconcileCaf` need no guard (`textContent`, classes, properties). `renderFoot`/`renderAttn` re-run an open popover's paint on every event, so the three footer popovers (`usagePop`, `costPop`, `attnPop`) carry the same last-written-string guard; they hold `data-sel` buttons, i.e. exactly the dropped-click hazard below. Most events change nothing a surface shows (~84% of sidebar repaints were byte-identical); this is not diffing and does not weaken render-everything: it is "skip when nothing changed", where measured. Measure any new `renderAll` surface before assuming it is free.

**On an interactive surface the guard is doing correctness work**: an `innerHTML` assignment destroys the node under the pointer, giving a restarted CSS transition, an emptied `<input>` (`#dashNote` lost a note mid-typing), and worst, **a dropped click** (replace between mousedown and mouseup → the `click` fires on the container → `closest()` finds nothing; a permission *Allow* was silently discarded). None of this shows on an idle fleet, which is the state the app is developed in. **A repaint-per-event surface carrying buttons or inputs needs the guard before it ships.**

Two things make a guard *effective*: **no per-second clock in the markup** (`dwellText` made the inspector's string differ every second by construction; it is now emitted empty and filled by `tickDwell` via `textContent`), and **invalidate wherever another module writes the same element**. `#inspector` keys on `dom.ts`'s `stageGen` (bumped by `takeStage`), `openDashboard` clears its own cache on entry; `dom.ts` owning the counter keeps the leaf module dependency-free.

The sibling hazard, where a poll compares a *model* rather than a rendered string: **a signature must list every field the markup prints**, and the two are edited in different files, so nothing makes them move together. `refreshSessionStats` (panes.ts) and the dirty poll (mirror.ts) each hash a `DiffStat` to decide whether the change is worth a repaint; when the working-set card started printing `dirty` (git's own count of the entries `files` misses), a stat differing only in that field would have been dropped as "nothing changed". The failure is invisible in the direction that matters — a stale figure, not a wrong one.

**When you measure a render function, force layout or the number is a lie**: `innerHTML` defers style/layout to the next frame, which a benchmark loop never reaches, so read `document.body.offsetHeight` after each call (`renderSidebar`: 0.13ms without, 7.0ms with).

## The needs-you set: two stamps, one sync, and a light that isn't in the markup

`needsYou` (./grouping) is the raw fact — a permission, a failed turn, a finished one, a red run. Two fields on `Sess` hang off it and **nothing else reads either**: `attnAt` is when the pane entered that set (0 when it isn't in it), `seenAt` the last time you put it on the stage. `seenAt >= attnAt` is therefore "you have looked at this since it started wanting you", which is the single question behind both halves of the feature — so a click cannot clear the badge without also stopping the highlight, and there is no set of acknowledged ids to keep in sync with the session map.

**`attnAt` is stamped in exactly one place: `syncAttn()`, first line of `renderAllNow`.** Not `phaseSince`, which a permission does not move at all; and not at the events, because there are five ways into the set (`Stop`, `StopFailure`, a `PermissionRequest` on its own channel, a task's exit code, and a fan-out's grace window expiring, which no event announces). All five already end in `renderAll()` by the app's oldest rule, so asking once per paint is both complete and self-healing — `was` is read back off the stamp, so running it twice changes nothing. Being one frame late does not show on a highlight measured in seconds.

**`needsYou` stays raw and `attnPending` is the filtered one** (needs you *and* you haven't been). They cannot be merged: `syncAttn` asks `needsYou`, so a predicate that answered "no, you've seen it" would clear the very stamp that decides whether you have, and the two would flip each other on alternate paints. Everything that *counts* sessions at you reads `attnPending` — the reactor badge and its picker, the tray title, the palette's "Needs you" group, a collapsed group's warning glyph. A blocking permission is exempt from clearing at all: looking at one is not answering it.

**The highlight is not in the markup, for a reason the guard section above only half covers.** `#projects` is rebuilt under a busy fleet several times a second, and a `lit` class re-applied to the fresh node replays the animation from zero — so a 4s highlight would glow for as long as anything else in the rail was moving. What the row actually needs is *how far through the fade it is*, which would make the markup differ on every repaint and leave the byte-identical guard off for the whole of it. So `applyFlash` (./sidebar) applies the class outside the render path with a **negative `animation-delay`** that resumes the fade where the clock is — the same trick, and the same trap, as peek's arming hairline. Two consequences worth keeping: the animation carries **no fill mode** (a filled value outranks every normal rule, so a finished `both` would keep painting over `.srow:hover` for as long as the class lingered), and reduced motion gets a flat tint instead of a fade, which is why the class has to actually come off — hence the one timeout to `attnFlashDeadline`.

## Pane invariants: WebGL pool, keystrokes, clipboard

**WebGL contexts come from a small LRU pool** over recently-staged panes (`attachWebgl`/`detachWebgl` in `terminal.ts`, handle in `Sess.gl`, `GL_POOL_MAX` = 8); spawners load none, `setActive` attaches on the way to the stage. Both simpler designs were tried and are wrong: a context per pane for life hits the webview's 16-context cap and silently downgrades the *oldest* panes to the slow DOM renderer; dispose-per-switch churns contexts and WKWebView punishes it once GC lags: JS cannot destroy a context, only unreference it, and `loseContext()` is worse (lost-but-referenced stays in WebKit's budget; eviction then trips INVALID_OPERATION, both observed). Warm panes re-attach free; `isExited`/closed panes free their slot; a context lost anyway dlogs and heals on next activation. Same lifecycle: an ended **claude** pane gives up its scrollback off-stage (`trimScrollback`: the transcript is on disk, a failed task's scrollback IS its log and shells have none, so both keep theirs), and `isExited` panes leave the 4s poll and the quit-guard count.

**Claude-pane keystrokes go through `claudeInput`** (`terminal.ts`): the first `^C` is forwarded, a repeat inside `INTR_GUARD_MS` swallowed, because a fast double `^C` exits the REPL and strands a dead pane; ending a session is explicit (✕, ⌘K, `/exit`). Windows Ctrl+V is `winClaudePaste` via `attachCustomKeyEventHandler`, and **xterm keeps only ONE such handler**, so a new key rule belongs in `claudeInput`/`winClaudePaste` (claude), `shellKeys` (shell) or `clipboardKeys` (task), never in a second call; no pane is more than one kind.

**Shell/task copy-paste is Ctrl+Shift+C/V** (the unshifted pair is taken: `^C` is the interrupt, xterm eats `^V`), the same chords as Windows Terminal and VS Code; ⌘C/⌘V reach the WebView natively. It goes through **`tauri-plugin-clipboard-manager` rather than `navigator.clipboard`** (`clipboard-read` raises OS permission prompts, and wry only auto-grants with `enable_clipboard_access()`, which Tauri leaves off), and pastes via `term.paste` rather than `write_pty` (bracketed paste, `\r\n`→`\r`).

**On Windows a non-ASCII keystroke leaves as a win32 input record rather than as text** (`win32_input_encode` in `pty.rs`, behind the `Session.win32_input` flag the reader latches from ConPTY's `ESC[?9001h`). ConPTY does not deliver a terminal's bytes to the child; it *parses* them into console key events, and a character it can best-fit into the OEM code page is synthesized as an **Alt+numpad sequence whose character rides on the key-UP record**. `_getwch` (the Windows CRT call behind Python's `getpass`, i.e. behind every "Enter your key:" prompt a script shows you) reads key-**down** records only, so those characters were dropped from the secret: **54 of 86 sampled non-ASCII characters never arrived**, `U+00A0` among them (what a passphrase copied out of a document carries). Silent both ways: nothing echoes at a hidden prompt, and gpg answers `Bad session key`, its ordinary *wrong-passphrase* error, so the search starts in the secret store. Windows Terminal is immune because it answers `ESC[?9001h` with key records; that is the whole of "it works in a normal console". Two rules hold the fix in place: **ASCII is never re-encoded** (all 95 printable characters round-trip exactly as text, verified, so `^C`, arrows, chords and Claude Code's TUI keep byte-identical input), and **an escape sequence is copied through untouched**, so a paste keeps the brackets the child asked for. `Uc` is a UTF-16 code unit: a non-BMP character is two record pairs. Guarded by `secret_input_reaches_the_child_byte_exact`, which drives a real PTY and reads its secret the way `_getwch` does; read it any other way and it passes with the bug present.

**Left standing, and known**: an *unsolicited* CSI reply is re-read by conhost as a function key: `\x1b[24;1R` (a cursor-position report) arrives at the child as `\x00=`, i.e. F3, so a terminal that answers a DSR nobody asked for corrupts whatever is reading input. Episko does not: ConPTY's own startup `ESC[6n` is consumed by conhost even when the answer comes back late (measured to 600ms, well past our event round-trip), and nothing else queries. Worth knowing before adding any code that replies to the child on its own.

## Telemetry-path invariants: StopFailure, storage cadences, logging

**A turn that died ends in `error`, and only one hook knows which it was**: `StopFailure` (not `Stop`) fires when the API kills a turn, carrying an `error` enum and `error_details`. Everything after looks identical to a clean finish (the same 60s idle `Notification` arrives either way) and unguarded it turned the red ✕ green a minute later (shipped; hence `Sess.apiErr`). Set by `StopFailure`, cleared only when the session genuinely starts another turn (`UserPromptSubmit`/`PreToolUse`/`SessionStart`/`SessionEnd`); **`endTurn` is the single place deciding done vs. error** (both `Stop` and the idle nudge route through it; run-on-stop is skipped while set). Every surface reads `phaseText(s)`, never `PILL_TEXT[s.phase]`, so the reason travels with the glyph.

**`endTurn` has a third answer, and `done` is never absorbing.** Claude Code fires
`UserPromptSubmit` the instant you press Enter — including mid-turn, because a message
typed then is queued rather than refused — so the outstanding turn's `Stop` lands *after*
the new prompt. Taken at face value that `Stop` marks the session "your turn" moments
before it starts the work you just asked for, and the tool guard in `applyHook` used to
read a bare `s.phase === "done"`, which made the lie permanent: from that `Stop` on, no
`PreToolUse`/`PostToolUse` could move the session at all, and only a *further*
`UserPromptSubmit` (already spent) could. The row showed a green tick, chimed, raised the
badge and fired run-on-stop over a pane that then worked for twenty minutes. Two halves
fix it, and both matter — 31 of the 36 stuck turns in six days of logs had no queued
prompt behind them at all, just a turn the model carried on by itself:

- **`Sess.queuedPrompt`** is set when a prompt arrives while the session is `working`,
  and consumed by exactly one `Stop`, which then reads `thinking` instead of `done` and
  skips run-on-stop (a run there verifies work about to change under it). A **flag, not a
  count**: 23 of 25 queued runs in those logs answered two or more prompts in a single
  turn, so a counter would have been left holding a phantom prompt and would have
  withheld the badge until the 60s idle nudge — trading a lie for a silence. That nudge
  clears it either way, which is the repair for the one case that strands it (a queued
  prompt cancelled with Esc fires no `Stop`).
- **`STRAGGLER_MS`** (2s) bounds the guard the flag cannot cover. The hooks are
  fire-and-forget `curl`s spawned concurrently, so a turn's last `PostToolUse` genuinely
  can land after its `Stop` and must not repaint the pane `working` a moment after the
  badge was earned — but only by the width of a process spawn. Past that window a tool
  hook is new work by definition; the logs hold a `PreToolUse` **996 seconds** after the
  `Stop` that was still suppressing it. Both ways of being wrong here self-correct (too
  wide: `done` until the turn's next tool call; too narrow: a `working` flicker until the
  idle nudge). Unbounded was the only version with no correction at all.

**A turn that ended while its agents run on is the background fan-out.** The `Workflow` tool returns a run id in about two seconds and the agent stops talking, so `Stop` fires, the phase goes `done`, and the whole cockpit read "your turn" for the twenty-odd minutes its fleet kept working: a green ✓ in the sidebar, a row in the reactor badge and the tray title, "waiting 17:33" in the inspector, a place in the attention sort, all for the one session that wanted nothing from you. The only trace of thirteen live agents was a `1 subagent` chip.

*Everything it shows comes from telemetry Episko already receives*, which is why there is no backend half and nothing to poll:

- **`PreToolUse{tool_name:"Workflow"}` carries the whole script**, and a workflow script's `meta` is required to be a pure literal, so the run's name, its description and its phase titles are sitting in the hook payload, ~2s before the turn ends. `parseWorkflowMeta` lifts them with regexes (never `eval`, since this is arbitrary JS from a tool call) and **bounds its search to the literal**: `name:` and `title:` occur throughout the agent prompts below it, and an unbounded match labels the run with a word out of a prompt. A **resumed** run carries no script at all (`scriptPath` + `resumeFromRunId`), which once made every resume an unnamed fleet — so `startFanout` takes the whole `tool_input` and recovers the name from the persisted script's basename (`<meta.name>-<runId>.js`), preferring the record the pane already holds when the two agree, since it also has the description and phases a filename cannot.
- **`SubagentStart`/`SubagentStop` fire on the PARENT for every agent a fan-out spawns**, workflow fleets included: 53 of each for a 53-agent run, measured off `episko.log`. Both payloads carry **`agent_id` and `agent_type`**, so `Sess.agents` holds the ones still up *by name* — the same argument as pairing a tool call's Pre and Post by `tool_use_id`. It replaced a bare `subagents` counter, and the difference is not tidiness: a counter can only drift up (a replayed POST, a Stop that never came) with nothing able to notice, and a leftover it produced was an unexplained gap between two figures rather than a named agent the card can point at. A payload with **no** id still works — a synthetic id in, oldest-outstanding out — because the readout must not vanish on an older CLI. The cumulative pair, the name and the phases ride `Sess.fanout` beside it.
- **Claude Code's own run-state JSON is not an option.** `~/.claude/projects/<slug>/<sid>/workflows/wf_*.json` has everything (per-agent labels, models, tokens, states) and is **created when the run finishes** (creation time == modification time == end time, on every run on disk). It knows nothing while it matters. `journal.jsonl` beside it *is* appended live, and still says less than the hooks do.

`liveFanout` is what every surface asks. One live agent has to be sufficient on its own: a workflow agent can run eighteen minutes without the parent seeing one event, so a rule needing recent activity drops the longest runs first. The **90s grace window** past the last event is not smoothing: a workflow runs plain JS *between* its fan-outs (a barrier collects, code dedupes, the next `parallel()` spawns), and through that gap the live count is legitimately 0 while the run is very much alive. Without the window the sidebar flips to a green ✓ and back on every stage boundary, which is worse than the bug. `bgWaiting` narrows it to the case that was wrong (no attention, no error, phase `done`/`idle`), so a blocking permission and a dead turn still outrank it, and a session mid-turn keeps its own `working` reading with the fleet showing as a tally beside it. `fanoutTally` owns the arithmetic for both the row and the bar, and its total is `max(started, done + running)` — where *running* is `liveCount`, which excludes leftovers past their own window: launching a second workflow over a live one restarts the counters, and `started` alone would draw a bar past its own end.

**Sufficient, but not forever — the set can hold agents nothing will ever retire.** A `SubagentStop` can genuinely never arrive: an interrupted workflow's agents, a turn the API killed, a silently dropped POST (`-s` + `async`, by design). Every miss leaves an agent outstanding and nothing takes it back out, so one lost Stop used to pin the "background" badge on a finished pane for the rest of the app's life — a real pane read **"2/8 ◑" an hour after its run-state file said completed**, off a day whose log held 7 Starts and 3 Stops (a workflow paused by API failures at midday, resumed at night). **Two windows** write them off, and which applies turns on one question: has a newer fan-out superseded the run that spawned this agent?

- **`FANOUT_DEAD_MS` (an hour)** writes off the whole fleet: far above the eighteen-minute silence above, and any real event re-stamps `lastAt` and revives the readout.
- **`ORPHAN_DEAD_MS` (fifteen minutes)** writes off a single agent a *newer* fan-out inherited. `startFanout` stamps `orphanedAt` on everything still up, because that call is the one moment the app knows those agents belong to a superseded generation. They keep counting — a second workflow launched over one still finishing is real work, and dropping them on sight would draw a bar past its own end — but on their own clock, because the hour is safe for a live fleet *only* by virtue of events that can revive it, and an orphan has no run left to report it. **This shipped**: four agents an interrupt killed at 19:30 were inherited by a fresh 34-agent workflow, and the pane read **"34 / 36" with all 34 of that run finished**, for hours, because every one of the new run's own events re-stamped the `lastAt` the leftovers were being measured against. The wrong number was the cheap half: `bgWaiting` kept the session out of the reactor badge, the tray title and the palette's "Needs you" group from 19:57 onward, reporting a session that wanted a human as one that was busy.

Both windows are applied on the **read** side, in `liveAgents`, and that is the load-bearing part: a session sitting `done` with a stale fleet receives no hooks at all, so a repair that only ran on the next event would never run — which is exactly how the stale count survived. `applyHook` sweeps the set too (expired orphans first, then the whole fleet once `liveFanout` has written it off) so the *state* catches up and no later fleet inherits the ghosts in turn, and so they cannot poison its `bg()` guard. Two more rules finish it: a `SubagentStart` with no live fleet mints a fresh record rather than resuming a retired one, which otherwise showed "12 of 14 done" for two agents that just launched; and **an inherited agent's Stop is credited to the run that spawned it, never to the one that inherited it** — counting it as progress here is how "34 / 34 done" was reached with two of the Stops behind that figure owed elsewhere.

What the surfaces do with a leftover is say so. The inspector card carries a `fo-orph` line under the bar (`↩ 2 still up from an earlier run · Explore`), the sidebar tooltip appends `(2 from an earlier run)`, and the debug snapshot spells out `34/34 done, 2 up, 2 inherited (Explore/Explore)`. They are counted in the fraction either way — the point is that a total which silently absorbs a previous run's agents is arithmetic nobody can check, which is why "34 / 36" read as a number rather than as a bug.

Two things that must move together: a status added to `GLYPH`/`GCLASS` needs a **`SHAPE` entry in `tray.ts`** (the tray falls back to the disc, so the symptom is a menu quietly showing the wrong state rather than a crash) and a **`--st-*` colour**, since `classRgb` reads the tray's ink out of the stylesheet. And **the fan-out card carries no clock**: the elapsed lives in `#iDwell`, which is patched by `textContent`; a time in that markup would make the string differ every second and permanently defeat `paintInspector`'s guard, on the surface that guard exists to protect.

Known and deliberately left alone: **run-on-stop still fires at the `Stop` that launched the fleet**, so a project's build/test rule can run over a tree thirteen agents are still writing to. Deferring it to the fan-out's end is the right shape, but the obvious guard (`bgWaiting`) also suppresses the rule for an ordinary session that used a `Task` subagent and then finished, which is a regression in a shipped feature to fix a rarer one. Wants its own change.

**A `localStorage` write on the telemetry path is a disk write**: the statusLine fires every 10s per session plus event-driven re-runs. Three cadences, chosen deliberately: **eager** (`cc-usage`, small, and a crash-lost dollar can't be reconstructed); **only-when-changed** (`cc-cost-base`, which used to write the whole map on every statusLine, so an idle fleet wrote identical bytes once a second); **floored** (`cc-usage-detail` 30s, `cc-io` 60s, both flushed on `quit-requested` and forced across midnight; both derived/approximate, and `daySpend`'s `unattributed` row already renders what a crash-lost minute looks like). **Cap anything keyed by day** (`USAGE_MAX_DAYS`/`IO_MAX_DAYS` = 420): a daily key with no cap grows forever *and* re-serialises per write. `cc-icons` is the largest key but written once per project ever.

**Persistence is all `localStorage`**, every key prefixed `cc-` (~40 of them); `grep '"cc-'` for the current set.

**Debug console** (🐞): `dlog()`/`dbgSnapshot()`, flags unrouted telemetry and JS errors, mirrors a snapshot to `$TMPDIR/cc-launcher/episko-debug.json` so an external tool or agent can read live state. **Two tiers**: the snapshot is state-of-now and dies with a crash; the durable timeline is the rolling `episko.log` (+ `panic.log`) in the OS app-log dir (`tauri-plugin-log` + a panic hook, the only on-disk trace of a panic that unwinds cleanly), and every `dlog()` tees into it via `log_frontend` (`[ui]`), one time-ordered file. A log that stops without `exit · clean shutdown` is itself evidence. Snapshot = "what is it doing now"; log = "why did it die".
