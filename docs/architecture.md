# Architecture deep dives: backend & frontend

> Rules and their reasons, compressed. The full narratives live in git history (CLAUDE.md before the split). Trust the code over the docs when they disagree, and fix the doc in the same commit.

## AppState & the disk-I/O accounting

`AppState` holds the telemetry `port`, the `sessions` map (PTY master + writer + child killer each), `owned_pids`, `io_samples` (previous per-pid reading → the inspector's rate), `io_retired` (bytes of exited sessions, so the total doesn't fall on close), the held-open `pending` permission requests, and `caffeinate`.

**Both I/O fields are in-memory, so `all_sessions_resources` reports a *run* figure, which is why `cc-io` exists.** `addIo` banks each poll's increment into a per-day rollup off the same sample the live bars use; `ioDelta` clamps a drop to zero (a restart is the normal case, the same reasoning as `costDelta`). No back-fill: missing days are "not recorded", never zero, and `ioTotal()` answers **null** rather than `{r:0,w:0}`.

**The three windows (run/today/all) genuinely coincide at first** (one recorded day; a run's first poll banks the whole counter), which reads as a cycling control that does nothing. `ioSameNote` (pure, tested) names the coincidence and returns null on divergence; it compares the **rendered** strings rather than floats. The `⟳` beside the label is the affordance.

**The write is floored at a minute**: the poll runs every 4s while a session is on stage; persisting each reading would be ~900 writes/hour for a number read daily. Accumulation is per-poll (free); only `flushIo` writes, forced across midnight and on `quit-requested`. Skipping polls loses no bytes (cumulative counters + `io_retired`); the one real loss is the stretch after the last reading (`flushIo` persists, it does not sample).

**What a gap costs is the day the bytes are filed under**: buckets are credited when the poll *lands*, and the poll is gated three ways (`mirror`, on-stage, background-webview throttling), so a quiet stretch over midnight booked a whole evening's churn to the next morning, wrong in both directions. Two halves fix it, both needed: **`splitIo`** (pure, tested) spreads an increment over its window weighted by each day's wall-clock share (a bounded, unbiased guess whose parts sum exactly, clamping windows no polling gap explains) and a **60s heartbeat** in `main.ts` calls `pollIo` (a pure counter read; `refreshSessionStats` no longer spawns anything, since the working set comes from `dirtyByFolder`). The cadence is `IO_SAVE_FLOOR_MS` exactly, so the heartbeat cannot raise the write rate, and `addIo` returns early when the disk was idle. **A meter must not add to what it measures**, so keep any new sampler on that footing.

**Be honest about coverage**: the counters cover the `claude` processes only, nothing they spawn (verified: a child's 64MB write moves the parent's `proc_pid_rusage` by 0.0MB), so `cargo`, `pnpm`, `git` and test runs are invisible, so real churn is *higher* than shown. Expect physical writes at several times the logical bytes (APFS is copy-on-write and transcripts grow by small appends).

## The `innerHTML` guards on `renderAll`'s path

The pattern: build the markup every pass, assign only when the string differs from the last write. Guarded: `renderSidebar` (`#projects`), `renderMini` (`#railmini`), `renderInspector` (`#inspector`); `updateTray` diffs a signature; `dashboard.ts`'s `paint(id, html)` per surface. `syncStageButtons`/`reconcileCaf` need no guard (`textContent`, classes, properties). `renderFoot`/`renderAttn` re-run an open popover's paint on every event, so the three footer popovers (`usagePop`, `costPop`, `attnPop`) carry the same last-written-string guard; they hold `data-sel` buttons, i.e. exactly the dropped-click hazard below. Most events change nothing a surface shows (~84% of sidebar repaints were byte-identical); this is not diffing and does not weaken render-everything: it is "skip when nothing changed", where measured. Measure any new `renderAll` surface before assuming it is free.

**On an interactive surface the guard is doing correctness work**: an `innerHTML` assignment destroys the node under the pointer, giving a restarted CSS transition, an emptied `<input>` (`#dashNote` lost a note mid-typing), and worst, **a dropped click** (replace between mousedown and mouseup → the `click` fires on the container → `closest()` finds nothing; a permission *Allow* was silently discarded). None of this shows on an idle fleet, which is the state the app is developed in. **A repaint-per-event surface carrying buttons or inputs needs the guard before it ships.**

Two things make a guard *effective*: **no per-second clock in the markup** (`dwellText` made the inspector's string differ every second by construction; it is now emitted empty and filled by `tickDwell` via `textContent`), and **invalidate wherever another module writes the same element**. `#inspector` keys on `dom.ts`'s `stageGen` (bumped by `takeStage`), `openDashboard` clears its own cache on entry; `dom.ts` owning the counter keeps the leaf module dependency-free.

**When you measure a render function, force layout or the number is a lie**: `innerHTML` defers style/layout to the next frame, which a benchmark loop never reaches, so read `document.body.offsetHeight` after each call (`renderSidebar`: 0.13ms without, 7.0ms with).

## Pane invariants: WebGL pool, keystrokes, clipboard

**WebGL contexts come from a small LRU pool** over recently-staged panes (`attachWebgl`/`detachWebgl` in `terminal.ts`, handle in `Sess.gl`, `GL_POOL_MAX` = 8); spawners load none, `setActive` attaches on the way to the stage. Both simpler designs were tried and are wrong: a context per pane for life hits the webview's 16-context cap and silently downgrades the *oldest* panes to the slow DOM renderer; dispose-per-switch churns contexts and WKWebView punishes it once GC lags: JS cannot destroy a context, only unreference it, and `loseContext()` is worse (lost-but-referenced stays in WebKit's budget; eviction then trips INVALID_OPERATION, both observed). Warm panes re-attach free; `isExited`/closed panes free their slot; a context lost anyway dlogs and heals on next activation. Same lifecycle: an ended **claude** pane gives up its scrollback off-stage (`trimScrollback`: the transcript is on disk, a failed task's scrollback IS its log and shells have none, so both keep theirs), and `isExited` panes leave the 4s poll and the quit-guard count.

**Claude-pane keystrokes go through `claudeInput`** (`terminal.ts`): the first `^C` is forwarded, a repeat inside `INTR_GUARD_MS` swallowed, because a fast double `^C` exits the REPL and strands a dead pane; ending a session is explicit (✕, ⌘K, `/exit`). Windows Ctrl+V is `winClaudePaste` via `attachCustomKeyEventHandler`, and **xterm keeps only ONE such handler**, so a new key rule belongs in `claudeInput`/`winClaudePaste` (claude), `shellKeys` (shell) or `clipboardKeys` (task), never in a second call; no pane is more than one kind.

**Shell/task copy-paste is Ctrl+Shift+C/V** (the unshifted pair is taken: `^C` is the interrupt, xterm eats `^V`), the same chords as Windows Terminal and VS Code; ⌘C/⌘V reach the WebView natively. It goes through **`tauri-plugin-clipboard-manager` rather than `navigator.clipboard`** (`clipboard-read` raises OS permission prompts, and wry only auto-grants with `enable_clipboard_access()`, which Tauri leaves off), and pastes via `term.paste` rather than `write_pty` (bracketed paste, `\r\n`→`\r`).

**On Windows a non-ASCII keystroke leaves as a win32 input record rather than as text** (`win32_input_encode` in `pty.rs`, behind the `Session.win32_input` flag the reader latches from ConPTY's `ESC[?9001h`). ConPTY does not deliver a terminal's bytes to the child; it *parses* them into console key events, and a character it can best-fit into the OEM code page is synthesized as an **Alt+numpad sequence whose character rides on the key-UP record**. `_getwch` (the Windows CRT call behind Python's `getpass`, i.e. behind every "Enter your key:" prompt a script shows you) reads key-**down** records only, so those characters were dropped from the secret: **54 of 86 sampled non-ASCII characters never arrived**, `U+00A0` among them (what a passphrase copied out of a document carries). Silent both ways: nothing echoes at a hidden prompt, and gpg answers `Bad session key`, its ordinary *wrong-passphrase* error, so the search starts in the secret store. Windows Terminal is immune because it answers `ESC[?9001h` with key records; that is the whole of "it works in a normal console". Two rules hold the fix in place: **ASCII is never re-encoded** (all 95 printable characters round-trip exactly as text, verified, so `^C`, arrows, chords and Claude Code's TUI keep byte-identical input), and **an escape sequence is copied through untouched**, so a paste keeps the brackets the child asked for. `Uc` is a UTF-16 code unit: a non-BMP character is two record pairs. Guarded by `secret_input_reaches_the_child_byte_exact`, which drives a real PTY and reads its secret the way `_getwch` does; read it any other way and it passes with the bug present.

**Left standing, and known**: an *unsolicited* CSI reply is re-read by conhost as a function key: `\x1b[24;1R` (a cursor-position report) arrives at the child as `\x00=`, i.e. F3, so a terminal that answers a DSR nobody asked for corrupts whatever is reading input. Episko does not: ConPTY's own startup `ESC[6n` is consumed by conhost even when the answer comes back late (measured to 600ms, well past our event round-trip), and nothing else queries. Worth knowing before adding any code that replies to the child on its own.

## Telemetry-path invariants: StopFailure, storage cadences, logging

**A turn that died ends in `error`, and only one hook knows which it was**: `StopFailure` (not `Stop`) fires when the API kills a turn, carrying an `error` enum and `error_details`. Everything after looks identical to a clean finish (the same 60s idle `Notification` arrives either way) and unguarded it turned the red ✕ green a minute later (shipped; hence `Sess.apiErr`). Set by `StopFailure`, cleared only when the session genuinely starts another turn (`UserPromptSubmit`/`PreToolUse`/`SessionStart`/`SessionEnd`); **`endTurn` is the single place deciding done vs. error** (both `Stop` and the idle nudge route through it; run-on-stop is skipped while set). Every surface reads `phaseText(s)`, never `PILL_TEXT[s.phase]`, so the reason travels with the glyph.

**A `localStorage` write on the telemetry path is a disk write**: the statusLine fires every 10s per session plus event-driven re-runs. Three cadences, chosen deliberately: **eager** (`cc-usage`, small, and a crash-lost dollar can't be reconstructed); **only-when-changed** (`cc-cost-base`, which used to write the whole map on every statusLine, so an idle fleet wrote identical bytes once a second); **floored** (`cc-usage-detail` 30s, `cc-io` 60s, both flushed on `quit-requested` and forced across midnight; both derived/approximate, and `daySpend`'s `unattributed` row already renders what a crash-lost minute looks like). **Cap anything keyed by day** (`USAGE_MAX_DAYS`/`IO_MAX_DAYS` = 420): a daily key with no cap grows forever *and* re-serialises per write. `cc-icons` is the largest key but written once per project ever.

**Persistence is all `localStorage`**, every key prefixed `cc-` (~40 of them); `grep '"cc-'` for the current set.

**Debug console** (🐞): `dlog()`/`dbgSnapshot()`, flags unrouted telemetry and JS errors, mirrors a snapshot to `$TMPDIR/cc-launcher/episko-debug.json` so an external tool or agent can read live state. **Two tiers**: the snapshot is state-of-now and dies with a crash; the durable timeline is the rolling `episko.log` (+ `panic.log`) in the OS app-log dir (`tauri-plugin-log` + a panic hook, the only on-disk trace of a panic that unwinds cleanly), and every `dlog()` tees into it via `log_frontend` (`[ui]`), one time-ordered file. A log that stops without `exit · clean shutdown` is itself evidence. Snapshot = "what is it doing now"; log = "why did it die".
